    CUPTI 程序計數器 (PC) 連續採樣教程

    GitHub 倉庫和完整教程可在 https://github.com/eunomia-bpf/cupti-tutorial 獲取。

    簡介

    程序計數器 (PC) 採樣是一種強大的分析技術，允許您在彙編指令級別瞭解 CUDA 內核的執行時間分佈。本教程演示如何實現連續 PC 採樣，可以監控任何 CUDA 應用程序，無需修改源代碼。

    您將學到什麼

    • 如何構建用於 PC 採樣注入的動態庫
    • 連續分析 CUDA 應用程序的技術
    • 理解 PC 採樣數據和停頓原因
    • 跨平臺實現（Linux 和 Windows）
    • 將分析庫與現有應用程序配合使用

    理解 PC 連續採樣

    PC 連續採樣與其他分析方法的不同之處在於：

    1. 在彙編級別操作：提供對實際 GPU 指令執行的洞察
    2. 無需源代碼修改：可以分析任何 CUDA 應用程序
    3. 通過庫注入工作：使用動態加載攔截 CUDA 調用
    4. 提供停頓原因分析：顯示線程束為什麼沒有取得進展
    5. 支持實時監控：可以在執行期間觀察性能

    架構概覽

    連續 PC 採樣系統包含：

    1. 動態庫：libpc_sampling_continuous.so（Linux）或 pc_sampling_continuous.lib（Windows）
    2. 注入機制：使用 LD_PRELOAD（Linux）或 DLL 注入（Windows）
    3. CUPTI 集成：利用 CUPTI 的 PC 採樣 API
    4. 輔助腳本：libpc_sampling_continuous.pl 便於執行

    詳細組件分析

    1. 輔助腳本 (libpc_sampling_continuous.pl)

    Perl 腳本作為包裝器，簡化了 PC 採樣過程。以下是其工作原理：

    腳本工作流程

    7. 緩衝區大小：驗證臨時緩衝區和硬件緩衝區大小

    8. 構建命令行選項字符串傳遞給注入庫

    關鍵配置參數

    參數 描述 默認值 有效範圍
    --collection-mode 採樣模式（1=連續，2=序列化） 1 1-2

    --hw-buf-size 硬件緩衝區大小 512 MB 任意大小
    --pc-config-buf-record-count 配置的 PC 記錄數 5000 任意數量
    --pc-circular-buf-record-count 每個循環緩衝區的記錄數 500 任意數量
    --circular-buf-count 循環緩衝區數量 10 任意數量
    --file-name 輸出文件名 pcsampling.dat 任意名稱

    2. 核心實現 (pc_sampling_continuous.cpp)

    C++ 實現通過 CUPTI 回調和數據收集處理實際的 PC 採樣。

    初始化流程

    1. 入口點（InitializeInjection，第 987-1025 行） 
      extern "C" int InitializeInjection(void) {
    // 讀取環境參數
    ReadInputParams();

    // 訂閱 CUPTI 回調
    CUPTI_API_CALL(cuptiSubscribe(&subscriber, 
                   (CUpti_CallbackFunc)&CallbackHandler, NULL));

    // 為所有內核啟動變體啟用回調
    CUPTI_API_CALL(cuptiEnableCallback(1, subscriber, 
                   CUPTI_CB_DOMAIN_DRIVER_API, 
                   CUPTI_DRIVER_TRACE_CBID_cuLaunchKernel));
    // ... 更多啟動回調

    // 啟用資源回調
    CUPTI_API_CALL(cuptiEnableCallback(1, subscriber, 
                   CUPTI_CB_DOMAIN_RESOURCE, 
                   CUPTI_CBID_RESOURCE_CONTEXT_CREATED));
}

    回調系統

    1. 主回調處理程序（CallbackHandler，第 758-983 行） 

      void CallbackHandler(void *pUserdata, 
                    CUpti_CallbackDomain domain,
                    CUpti_CallbackId callbackId, 
                    void *pCallbackData) {
    switch (domain) {
        case CUPTI_CB_DOMAIN_DRIVER_API:
            // 處理內核啟動
            HandleDriverApiCallback(callbackId, pCallbackData);
            break;
        case CUPTI_CB_DOMAIN_RESOURCE:
            // 處理上下文和模塊事件
            HandleResourceCallback(callbackId, pCallbackData);
            break;
    }
}

      bool GetPcSamplingDataFromCupti(
    CUpti_PCSamplingGetDataParams &params,
    ContextInfo *pContextInfo) {
    // 分配循環緩衝區

    清理和退出

    1. 退出處理程序（AtExitHandler，第 595-673 行） 
      void AtExitHandler() {
    // 為所有活動上下文禁用 PC 採樣
    for (auto& itr: g_contextInfoMap) {
        // 刷新剩餘數據
        while (itr.second->pcSamplingData.remainingNumPcs > 0) {
            GetPcSamplingData(pcSamplingGetDataParams, itr.second);
        }

        // 禁用採樣
        cuptiPCSamplingDisable(&pcSamplingDisableParams);

        // 排隊最終緩衝區進行寫入
        g_pcSampDataQueue.push(
            std::make_pair(&itr.second->pcSamplingData, 
                         itr.second));
    }

    // 加入工作線程並清理
    g_thread.join();
    FreeAllocatedMemory();
}

    高級配置

    性能調優

    1. 採樣週期優化
    2. 較低值（5-10）：高細節，更多開銷
    3. 中等值（11-20）：平衡方法

    4. 較高值（21-31）：低開銷，較少細節

    5. 緩衝區大小考慮 

      臨時緩衝區大小 = (預期 PC 數) × (16 字節 + 16 字節 × 停頓原因數)

示例：1000 個 PC，4 個停頓原因
= 1000 × (16 + 16 × 4)
= 1000 × 80 字節
= 最少 80 KB

    6. 收集模式選擇

    7. 連續模式：最適合長時間運行的內核
    8. 序列化模式：更適合短暫、頻繁的內核啟動

    內存管理

    系統使用多緩衝區方法：

    1. 配置緩衝區：保存 PC 採樣設置（默認：5000 條記錄）
    2. 循環緩衝區：收集數據的臨時存儲（默認：10 個緩衝區 × 500 條記錄）
    3. 硬件緩衝區：GPU 端存儲（默認：512 MB）
    4. 臨時緩衝區：數據處理的工作內存（默認：1 MB）

    停頓原因分析

    常見停頓原因及其含義：

    停頓原因 描述 優化策略
    MEMORY_DEPENDENCY 等待內存操作 改善內存合併，使用共享內存
    EXECUTION_DEPENDENCY 等待先前指令 重新排序指令，增加 ILP
    NOT_SELECTED 線程束未被調度 平衡工作負載，減少分歧
    SYNCHRONIZATION 在同步點等待 最小化 __syncthreads()，優化屏障
    TEXTURE 等待紋理獲取 優化紋理緩存使用
    CONSTANT_MEMORY 等待常量內存 對頻繁訪問的常量使用共享內存

    故障排除

    常見問題和解決方案

    1. 庫加載失敗 

      錯誤：庫 libpc_sampling_continuous.so 不存在
      解決方案：確保 LD_LIBRARY_PATH 包含庫目錄

    2. CUPTI 初始化錯誤 

      CUPTI_ERROR_NOT_INITIALIZED
      解決方案：驗證 CUDA 和 CUPTI 版本匹配

    3. 緩衝區溢出 

      警告：cuptiPCSamplingDisable() 期間丟棄了 N 條記錄
      解決方案：使用命令行參數增加緩衝區大小

    4. 權限被拒絕 

      無法打開文件進行寫入
      解決方案：確保輸出目錄中的寫入權限

    性能影響

    PC 採樣開銷取決於：

    1. 採樣頻率：頻率越高 = 開銷越大
    2. 內核持續時間：較長的內核分攤設置成本
    3. 緩衝區大小：較大的緩衝區減少刷新頻率
    4. 收集模式：連續模式的開銷低於序列化模式

    典型開銷範圍： - 低採樣（週期=20-31）：1-5% 開銷 - 中等採樣（週期=10-19）：5-15% 開銷 - 高採樣（週期=5-9）：15-30% 開銷

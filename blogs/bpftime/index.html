    bpftime: 讓 eBPF 從內核擴展到用戶空間

    鄭昱笙，於桐

    eBPF 是一項革命性的技術，起源於 Linux 內核，可以在操作系統的內核中運行沙盒程序。它被用來安全和有效地擴展內核的功能，而不需要改變內核的源代碼或加載內核模塊。

    在這篇 Blog 中，我們希望向大家介紹一個全新的開源用戶態 eBPF 運行時：https://github.com/eunomia-bpf/bpftime 。bpftime 進一步拓展了 eBPF 的能力，使現有的 eBPF 工具和應用，例如 BCC tools, bpftrace, Deepflow 等，能夠不需要進行代碼修改即可在非特權用戶空間運行，同時使用和內核 eBPF 相同的庫和工具鏈。

    bpftime 不僅提供了 Uprobe 和系統調用追蹤點等動態追蹤或擴展機制，還相比內核 Uprobe 有一個數量級的性能提升，並且和內核 eBPF 一樣，無需手動進行代碼插樁或重啟進程。bpftime 通過用戶態共享內存支持進程間 eBPF maps，同時兼容內核 eBPF maps，能夠實現與內核 eBPF 基礎設施的無縫操作。此外，它包含了針對多種架構的高性能 LLVM JIT/AOT 編譯器，以及針對 x86 的輕量級 JIT 和解釋器。通過性能數據和實際案例，我們也將展示 bpftime 如何在現實世界中發揮作用，並對其未來發展進行展望，希望 bpftime 能為系統監控、分析和擴展帶來前所未有的性能和靈活性。在 Linux plumbers 23 會議上，我們也介紹了 bpftime 的設計和實現[2]。

    eBPF: 從內核態到用戶態的系統擴展

    eBPF（擴展的 Berkeley Packet Filter）從最初的網絡數據包過濾工具，已經演變為一個多功能的系統級擴展技術。自從 20 世紀 90 年代 BPF 的誕生以來，eBPF 通過擴展指令集和與內核數據結構的直接互動，顯著增強了其功能。2014 年加入 Linux 內核後，eBPF 成為一個強大的字節碼引擎，廣泛應用於性能分析、安全策略等領域。隨著計算環境的複雜化，eBPF 的實時數據採集和分析能力在現代計算中發揮了重要作用，尤其是在流量控制、負載均衡和安全策略等方面。

    雖然 eBPF 最初是為內核設計的，但它在用戶空間的巨大潛力，以及內核對於 GPL LICENSE 的限制，也催生了例如 ubpf[3] 和 rbpf[4] 這樣早期的用戶空間 eBPF 運行時的產生。這種運行時使開發者能夠在內核之外運行 eBPF字節碼，突破了 GPL 許可的限制，同時提供了更加直觀和方便的調試環境。但是，編寫適用於 ubpf 和 rbpf 的程序可能需要一個特定的、和內核不完全兼容的工具鏈，同時只有有限的單線程哈希 maps 實現，難以運行實際的 eBPF 程序。另外，ubpf 和 rbpf 本身只是一個執行 eBPF 字節碼虛擬機，在實際的使用中，依然需要編寫膠水代碼，和其他用戶空間程序進行編譯、鏈接後才能使用，它們本身也不提供動態追蹤的功能。

    在實際應用中，用戶態 eBPF 已被嘗試擴展和應用於網絡處理、區塊鏈和安全等領域。例如，Oko 和 DPDK eBPF 支持展示了 eBPF 在網絡數據處理中的靈活性和性能優勢。Solana 項目利用 eBPF 實現了 JIT 編譯器，為區塊鏈智能合約執行提供支持。eBPF for Windows 項目則是將 eBPF 功能擴展到 Linux 之外，展現了 eBPF 在跨平臺兼容性方面的潛力。這些應用案例不僅展示了 eBPF 強大的系統擴展能力，也突顯了它在現代計算領域的重要性和廣泛適用性。更進一步的討論可以參考我們之前的 Blog: https://eunomia.dev/blogs/userspace-ebpf/

    為什麼我們需要 bpftime

    由於操作系統內核的核心作用以及對穩定性和安全性的高要求，操作系統內核的創新和演化相對來說較慢，這也是 eBPF 出現的初衷：在不改變內核源代碼的情況下，擴展內核的功能，並進一步帶來更多的創新性應用場景[5]。這也是我們希望 bpftime 能夠帶來的影響：在不改變用戶空間程序代碼的情況下，藉助 eBPF 帶來的安全性和生態，探索更多的發展可能性，同時彌補當前內核態 eBPF, 和用戶態其他擴展方案可能的不足。

    內核態實現用戶態追蹤（Uprobe）和系統調用追蹤等的侷限性

    Uprobe 是一種強大的用戶級動態追蹤機制，它允許開發者在用戶空間的程序中進行動態插樁，例如在函數的入口點、特定的代碼偏移位置，以及函數的返回點。這種技術的實現是通過在指定的位置設置斷點，例如在 x86 架構上使用 int3 指令，當執行流到達這一點時，程序會陷入內核，觸發一個事件，隨後執行預定義的探針函數，完成後返回用戶態繼續執行。這種動態追蹤方法能夠在系統範圍內跟蹤和插樁所有執行特定文件的進程，即允許在不修改代碼、重新編譯或重啟進程的情況下，收集性能分析和故障診斷的關鍵數據。

    但是，由於 eBPF 虛擬機在內核態執行，當前的 Uprobe 實現在內核中引入兩次上下文切換，造成了顯著的性能開銷，特別是在延遲敏感的應用中這種開銷會嚴重影響性能。如圖所示，和 Kprobe 相比，Uprobe 的開銷接近十倍[5]。另一方面，Uprobe 目前也僅限於追蹤，無法修改用戶態函數的執行流程，或者修改函數的返回值，這也限制了 Uprobe 的使用場景，無法進行代碼擴展、熱補丁、缺陷注入等操作。儘管如此，Uprobe 依舊因其非侵入式的用戶空間功能追蹤而在生產環境中被廣泛採用，用於追蹤諸如 SSL/TLS 和 HTTP2 等用戶空間協議，監控內存分配和內存洩漏，分析垃圾回收和語言運行時，跟蹤協程的創建和回收等等場景。

    對於系統調用的 tracepoint，由於它們是全局可見的，因此對於特定進程的追蹤而言，需要進行額外的過濾，例如針對 pid、cgroup 等在 eBPF 中進行過濾[6]，這也會對其他不需要被跟蹤的進程帶來一些額外的開銷。

    內核態 eBPF 安全性和擴展性的限制

    在內核態運行的 eBPF 有其安全性和擴展性的限制。一方面，eBPF 程序需以內核模式運行，這意味著需要 root 權限，從而增加了攻擊面並帶來潛在的風險，例如容器逃逸。此外，eBPF 自身的漏洞也可能導致內核層面的安全漏洞。另一方面，驗證器雖然對 eBPF 程序進行限制以保證安全，但這也限制了 eBPF 的功能擴展；任何想要添加的新功能或改進都需要對內核代碼進行修改。這些限制不僅增加了系統的維護難度，也降低了 eBPF 的靈活性和普適性。

    對於沒有 eBPF 支持的內核（例如低版本系統），或非特權容器中的應用而言，用戶態 eBPF 運行時也是一個可行的替代選項，可以允許在沒有內核 eBPF 支持的情況下，運行 eBPF 程序進行追蹤、分析、擴展等操作。

    其他用戶空間擴展方案的不足

    目前也有一些其他的用戶態追蹤和擴展方案，例如 gdb 等工具可以使用 ptrace 機制，對其他進程進行追蹤分析，Wasm、lua 虛擬機可以作為插件運行時使用，例如 Frida 這樣的二進制插樁工具，也可以在用戶態進行動態追蹤。但是，這些方案都有各自的侷限性。

    • 性能開銷較大：傳統的工具如 gdb 利用 ptrace 機制進行進程追蹤，雖然功能強大，但在其他進程進行分析和交互時會帶來顯著的性能開銷。這種方法會頻繁地暫停和恢復目標進程，導致效率降低。另外，ptrace 也限制系統中同時進行追蹤的進程數量，因此無法進行大規模的分佈式追蹤。WebAssembly (Wasm) 沙箱作為運行時插件，雖然具有良好的靈活性和跨語言支持，但它們在執行外部庫或過程時，需要進行嚴格的驗證和運行時檢查，可能引入性能損耗。相對而言，eBPF 提供了一個更為性能中心化的策略，使用靜態分析和驗證器確保了代碼在主機上的安全執行，而不需要運行時的額外開銷。對於 bpftime 而言，由於它是嵌入在被追蹤進程的函數調用上下文執行 eBPF 虛擬機，不需要經過額外的上下文切換，因此性能開銷更小。
    • 安全性問題：二進制插樁工具如 Frida 提供了動態追蹤的能力，但這可能會引入安全性問題，因為插樁代碼運行在相同的進程上下文中，可能會被惡意利用，同時追蹤工具或腳本本身的代碼缺陷也可能導致被追蹤的程序崩潰，例如訪問了錯誤的地址或者指針等。相比之下，eBPF 可以通過驗證器確保代碼的安全性。
    • 可見性不足：另外，對於其他的用戶態的追蹤方案而言，這些工具通常只能提供對單個進程的觀察能力，無法提供系統範圍內的洞察，難以捕獲內核態事件或跨進程通信的全局視圖，限制了其在複雜系統中的分析能力。這也就是 eBPF 和其它方案主要在內核態中進行追蹤的原因，可以關聯分析內核態和用戶態的事件，例如將七層的網絡數據包和內核態的網絡事件進行關聯，或者將用戶態的函數調用行為和內核態的系統調用進行關聯，從而提供更加全面的分析能力。對於 bpftime 而言，它可以不僅僅是一個用戶態的虛擬機方案，用戶態的 eBPF 可以和內核態中的 eBPF 基礎設施協同工作，來實現跨越邊界的分析和擴展能力。

    對於現存的其他用戶態的 eBPF 運行時，如前所述，它們沒有動態追蹤或動態擴展的能力，需要手動集成，也無法直接利用現有的 eBPF 工具鏈和應用，這很大程度上限制了它們的使用場景。另一方面，它們也沒辦法直接和內核態的 eBPF 協同工作，只能提供用戶態的有限擴展能力。

    bpftime：用戶態 eBPF 運行時

    和現有的 eBPF 工具和框架兼容的用戶態 eBPF 運行時

    bpftime 希望能保持和現有的內核 eBPF 的良好兼容性，作為內核 eBPF 的一種用戶態替代和改進方案，並且希望能最大程度上利用現有 eBPF 豐富的生態和工具。例如，bpftime 允許直接使用未經修改的 bpftrace 工具，在用戶態執行 eBPF 腳本，追蹤系統調用或用戶態函數：

    同時，也可以在用戶態運行 bashreadline，funclatency，gethostlatency，mountsnoop，opensnoop，sigsnoop，statsnoop，syscount 等 BCC/libbpf-tools 工具[7]。bpftime 在用戶態的共享內存之中構建了 eBPF maps 的數據結構實現，可以同時分析統計多個進程，也可以支持通過 ring buffer、perf buffer 等方式，將數據上報給追蹤工具。

    bpftime 也在用戶態提供了和內核兼容的 eBPF 基礎設施，可以在完全不需要內核 eBPF 的情況下運行，並且支持一部分內核的 eBPF maps，helpers，動態追蹤機制和幾乎所有的 eBPF 指令集：

    從安全性角度出發，bpftime 也提供了 eBPF 驗證器，用於驗證 eBPF 字節碼的安全性，防止惡意代碼的注入或者破壞被追蹤的進程。bpftime 可以使用內核態的 eBPF 驗證器，也可以使用另一個獨立的用戶態 eBPF 驗證器，作為無法訪問內核 eBPF 的替代方案。

    高性能的 Uprobe 和系統調用追蹤

    bpftime 支持 Uprobe 和系統調用追蹤，通過二進制重寫的方式，將 eBPF 程序嵌入到被追蹤進程的函數調用上下文中，從而實現動態追蹤和擴展。這種方法不僅避免了內核態和用戶態之間的上下文切換，還能夠在不修改代碼、重新編譯或重啟進程的情況下，收集性能分析和故障診斷的關鍵數據。和內核態的 Uprobe 相比，bpftime 的 Uprobe 實現性能更高，同時也提供了更多的功能，例如可以修改函數的返回值，或者修改函數的執行流程，從而實現代碼擴展、熱補丁、缺陷注入等操作。在用戶態實現的 Uprobe，性能可以比內核態的 Uprobe 高一個數量級：

    Probe/Tracepoint Types Kernel (ns) Userspace (ns)
    Uprobe 3224.172760 314.569110
    Uretprobe 3996.799580 381.270270
    Syscall Trace 151.82801 232.57691

    藉助 ptrace 實現的動態庫注入，和 LD_PRELOAD 等技術，bpftime 的 eBPF 運行時支持在程序啟動運行的時候進行追蹤，也支持將 eBPF 探針直接掛載到多個正在執行的進程。我們也進行了一個測試，通過 bpftime 加載一個監控 libc 中 malloc 函數的 eBPF 探針，並測量了加載延遲。結果顯示，bpftime 在加載過程中會使正在運行的進程暫停約 48 毫秒。作為比較，我們使用了 LD_PRELOAD 方法在進程開始前加載同樣的擴展，並觀察到其加載延遲為 30 毫秒。

    我們使用 sslsniff 工具[8]，在 bpftime 的用戶態 Uprobe 中對於 Nginx 的 SSL 加密流量進行了追蹤分析，並且和基於內核 Uprobe 的方式進行了對比，也可以觀察到明顯的性能提升：

    對於現代的 eBPF 可觀測性工具而言，可能需要對於同一個事件，在內核和用戶態函數同時進行採集分析。例如，對於一個 HTTP 請求，可能需要同時分析內核態的網絡事件，以及用戶態的函數調用，從而得到一個完整的請求鏈路。bpftime 的 Uprobe 實現可以和內核態的 eBPF kprobe 協同工作，從而實現這種跨越邊界的分析能力。對於其他的動態追蹤機制的實現和改進，也在我們的計劃之中。

    新的 eBPF JIT 編譯器和 AOT 編譯器

    bpftime 包含了一個新的基於 LLVM 的 eBPF JIT 編譯器，可以在運行時將 eBPF 字節碼編譯為本地機器碼，從而提高 eBPF 程序的執行效率。和 ubpf 和 rbpf 等其他用戶態 eBPF 運行時的 JIT 編譯器，以及和 Wasm 相比，LLVM JIT 編譯器可以提供更好的性能，接近 native 代碼的執行效率，同時也提供了更好的跨平臺支持，例如支持 RISC-V 等架構。我們進行了一個簡單的性能對比和分析[9]:

    除了 JIT 之外，bpftime 也包含了一個 AOT 編譯器，可以預先將 eBPF 字節碼驗證過後編譯為特定架構上的機器碼文件，以便在嵌入式上進行部署和使用，可以大大減少編譯啟動的時間。

    更多的探索性用例和未來發展

    除了擴展先前的 Uprobe 和系統調用追蹤點，bpftime 還可以用於其他的探索性用例，例如：

    • 錯誤注入：藉助和內核兼容的 bpf_override_return() helper[10]，bpftime 可以允許在特定 eBPF 程序類型中，修改進程的 Syscall 返回值，阻止特定的 Syscall，或者修改和替換特定的函數調用，從而實現錯誤注入的功能。內核的 Uprobe 本身並不支持這種功能，同時內核的 bpf_override_return 也由於安全原因，需要編譯時啟用 CONFIG_BPF_KPROBE_OVERRIDE 選項才能開啟，主流的 Linux 發行版默認不開啟這個選項。
    • 熱補丁：如上所述，藉助 bpf_override_return 的 helper 機制，userspace eBPF 也可以替換、過濾某些函數調用，從而實現熱補丁的功能。
    • 基於 eBPF 的 Nginx Module：bpftime 可以作為一個 Nginx Module，通過 eBPF 實現 Nginx 的擴展，例如在 Nginx 中實現動態路由、負載均衡、緩存、安全策略等功能。
    • 增強 Fuse：已經有一些使用內核中的 eBPF 來優化 Fuse 嘗試，bpftime 也可能可以作為用戶態文件系統的一部分，通過 eBPF 在對對應的用戶態進程中修改系統調用等的行為，實現對文件系統的擴展，例如在用戶態文件系統中實現動態路由、緩存、安全策略等功能。

    bpftime 目前還是一個較為早期的探索性項目，我們也在積極探索更多其他可能的應用場景，例如在用戶態實現 eBPF 的網絡數據包過濾，優化服務網格的數據包轉發性能，繞過內核的網絡協議棧等等，非常期待大家提出更多的想法和建議，或者和我們一起實現這些功能。之後，我們也希望 bpftime 能提供對內核更好的兼容性支持，藉助 LLVM 的 JIT 編譯器，可能也可以為內核的 eBPF 提供更好的性能優化指導、更方便的測試和調試環境。

    總結

    bpftime 在用戶空間為 eBPF 應用打開了新的可能性，也為擴展用戶態應用提供了一些新的選擇。它允許現有 eBPF 應用程序使用相同的庫和工具鏈在非特權用戶空間運行，併為用戶空間 eBPF 提供了 Uprobe 和 Syscall 等跟蹤機制，與內核 Uprobe 相比，性能有了顯著提高，而且無需手動檢測代碼或重啟進程。運行時支持用戶空間共享內存中的進程間 eBPF 映射，也兼容內核 eBPF 映射，允許與內核 eBPF 基礎架構無縫運行。

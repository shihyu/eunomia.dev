    深入GPU性能分析工具：現代加速器追蹤工具的實現詳解

    對異構加速器（GPU、DPU和APU）進行性能分析和追蹤對於優化現代系統的性能至關重要。本調研提供了一個深入的實現導向的綜述，介紹了當前最先進的工具如何捕獲低級執行細節。我們面向兩類受眾：(1) 工具開發者，他們希望瞭解現有性能分析工具的構建方式——包括它們鉤住的接口以及如何追蹤CPU和加速器；(2) 系統工程師，他們需要根據功能和開銷決定集成哪些工具。我們探討了關鍵性能分析工具的內部架構、它們攔截的運行時庫和驅動API、它們是否追蹤CPU、GPU或兩者上的事件，以及它們如何處理跨設備關聯。然後我們檢查實現策略（插樁vs採樣、性能計數器的使用、動態二進制插樁、內核鉤子如eBPF）以及GPU特定技術（如warp級指令採樣）。我們比較了數據處理和可視化方法，包括追蹤數據格式、存儲和導出方法，以及GUI/CLI/Web界面（與TensorBoard或Grafana等儀表板集成）。我們列出了這些工具收集的性能指標——從內核延遲和吞吐量到SM佔用率、緩存未命中和互連利用率——解釋了原始硬件計數器如何轉換為派生指標以及涉及的粒度/精度權衡。接下來，我們討論用戶可以從可視化（時間線、火焰圖、依賴圖等）中獲得的見解，例如檢測流水線停頓、內存瓶頸或CPU-GPU不同步。我們回顧了工具的可擴展性（對插件或用戶定義插樁的支持），以及不同測量技術的相對開銷和侵入性。我們還討論了安全和沙盒問題——例如，在容器化或多租戶環境中的性能分析——並概述了已知限制和未來方向（包括對新興DPU和集成CPU-GPU APU的支持）。本調研的目標是提供一個全面的系統級概述，超越功能列表，比較這些性能分析工具在底層的工作方式，包括開源工具使用的任何逆向工程或未記錄的方法。

    關鍵性能分析工具的內部架構

    瞭解每個工具的內部設計揭示了它能夠觀察軟件/硬件棧的哪些層次。下面我們回顧具有代表性的GPU性能分析和追蹤工具——包括廠商提供的和開源的——重點關注它們的架構、數據收集機制和目標平臺。

    NVIDIA Nsight Systems

    NVIDIA Nsight Systems是一個系統級性能分析工具，為CUDA應用程序提供CPU和GPU活動的時間線視圖。在內部，Nsight Systems結合了輕量級的CPU採樣和GPU活動追蹤。它利用Linux性能事件接口來捕獲CPU線程調度並對CPU指令指針進行採樣。實際上，這意味著它依賴於perf_event_open進行最小開銷的採樣，在Linux上需要適當的perf_event_paranoid設置。對於GPU追蹤，Nsight Systems通過NVIDIA的CUDA分析工具接口(CUPTI)與之交互，以在GPU操作發生時（內核啟動、內存複製等）接收回調"活動"記錄。通過鉤入CUDA驅動程序/運行時（通過CUPTI），Nsight Systems記錄每個GPU內核執行和內存傳輸的時間戳。它通過一個公共時間戳基準同步CPU和GPU時間線（CUPTI事件被時間戳標記並與CPU事件合併），使兩個處理器上的事件可以在統一的時間線中關聯起來。該工具還追蹤CUDA之外的各種運行時：它可以捕獲操作系統事件、存儲I/O和GPU加速庫（如cuDNN、cuBLAS）（當通過NVTX註釋進行插樁時）。Nsight Systems主要對GPU使用基於事件的插樁（通過CUPTI回調）和對CPU使用統計採樣，使其成為一種混合方法。這種設計實現了低開銷——通常只有幾個百分點——足以對完整應用程序進行分析。數據被記錄到專有的跟蹤文件（如.nsys-rep）中，可以在Nsight Systems GUI中查看或導出（CLI可以生成JSON或CSV摘要統計信息）。它支持多線程和多GPU追蹤，在時間線上顯示上下文切換和併發性。然而，作為廠商特定的工具，Nsight Systems專注於NVIDIA GPU以及CUDA或相關NVIDIA API；它不直接支持AMD或Intel GPU運行時。

    NVIDIA Nsight Compute

    Nsight Compute是NVIDIA的內核級性能分析器，用於對單個GPU內核進行深入分析。與提供時間線不同，它為每個內核啟動提供詳細的指標報告。在內部，Nsight Compute廣泛地對GPU硬件性能計數器進行插樁和測量。它使用NVIDIA的分析接口（如CUPTI的Event和Metric API或更新的CUDA Profiling API）來編程GPU性能監視器，以計算執行的指令、內存事務、warp佔用率等事件。由於GPU可用計數器有限，Nsight Compute通常會多次重放每個內核以收集所有請求的指標。例如，一個內核可能會運行數十次（例如46次）以收集不同的計數器集，這些計數器稍後會被聚合。這種事後插樁方法產生了全面的指標（包括派生指標，如已實現的佔用率或內存吞吐量），但會產生顯著的運行時開銷——因此Nsight Compute通常用於小型內核或選擇性分析會話。該工具的架構包括一個內核注入機制：它在每個內核啟動時暫停目標程序，設置計數器（甚至在內核周圍插入計時工具），然後恢復執行並收集結果。它僅支持NVIDIA GPU（從Volta架構開始）和主要是CUDA內核（儘管它也可以通過鉤住這些調用來分析來自GPU加速庫或CUDA圖的內核）。結果存儲在報告文件中或顯示在交互式GUI/CLI中，指標按"節"分組。Nsight Compute的指標計算系統非常先進——它使用工具中嵌入的公式從低級計數器計算高級統計數據（例如，已實現的佔用率、停滯原因細分）。輸出可以導出為文本或CSV以供進一步分析。雖然非常詳細，但Nsight Compute與NVIDIA驅動程序的緊密集成意味著它不能擴展到其他供應商，而且必須離線使用（對於連續監控來說太具侵入性）。

    AMD Omnitrace

    Omnitrace是由AMD研究院開發的開源性能分析和追蹤工具。其設計強調通過動態二進制插樁和採樣對CPU和GPU執行進行全面追蹤。Omnitrace可以附加到未修改的應用程序上，在運行時對函數調用（包括HIP和OpenCL API調用）進行插樁。在底層，它使用動態二進制插樁框架在目標程序的函數中插入探針（文檔暗示它可能使用Dyninst或類似工具）。用戶可以在執行前配置要插樁的函數或模塊，使他們能夠通過只選擇特定區域來限制開銷。在運行時，插樁會記錄進入/退出事件和時間戳，而並行的調用棧採樣組件定期對所有線程進行採樣，以捕獲CPU執行熱點。對於GPU工作，Omnitrace鉤入AMD的ROCm棧：它使用ROCm的roctracer回調來追蹤AMD GPU上的HIP運行時事件和GPU內核執行。（目前，Omnitrace僅通過HIP和HSA API支持AMD GPU——尚不支持NVIDIA GPU，反映了其AMD專注點）。收集的追蹤數據以開放的Perfetto格式（基於protobuf）寫入，可以在Chrome/Perfetto網頁查看器中可視化。這種格式選擇使得可以在任何瀏覽器中查看豐富的時間線視圖（Perfetto UI）。此外，Omnitrace生成聚合的性能分析（例如，每個函數的總時間、調用圖）以JSON和文本文件形式。JSON輸出與Hatchet等分析工具集成（它將數據加載到pandas中進行自定義分析）。由於其開源性質，Omnitrace的架構具有高度可擴展性：用戶可以修改它以支持新事件或使用其用戶API標記自定義區間。它有效地合併了統計性能分析器和追蹤器的功能，提供了高級摘要和完整執行追蹤。由於它在二進制級別進行插樁，存在一些開銷，但這通過讓用戶選擇採樣頻率和要插樁的函數來緩解。總體而言，Omnitrace提供了跨平臺性能分析器的藍圖（它設計為也可在僅CPU的應用程序上工作，支持任何CPU供應商，而GPU支持目前是AMD特定的）。

    Rice HPCToolkit

    HPCToolkit是一個長期存在的開源性能分析工具包，以其能夠以低開銷分析大型HPC代碼而著稱。它最近的擴展通過結合CPU採樣和GPU活動追蹤來支持GPU加速程序。HPCToolkit的內部架構使用供應商中立的GPU監控基礎。這個基礎連接到特定供應商的驅動程序：在NVIDIA上，它使用CUPTI；在AMD上，它使用ROC-tracer；對於Intel GPU，它包裝了Level Zero API。本質上，HPCToolkit註冊回調函數，以便每當GPU運行時（CUDA、HIP、Level0、OpenCL）啟動內核或執行數據傳輸時，HPCToolkit會收到通知。此外，HPCToolkit為OpenCL和Level Zero安裝自己的攔截包裝器，以捕獲在沒有內置跟蹤器的平臺上的事件。所有GPU事件（內核啟動開始/結束等）都被時間戳標記並記錄在GPU操作跟蹤中。同時，應用程序的CPU端通常通過採樣進行分析——HPCToolkit的hpcrun使用定時器或硬件計數器中斷對CPU線程的調用棧進行採樣，將成本歸因到代碼區域。這兩個數據源在分析過程中合併，以關聯CPU調用路徑與GPU活動。HPCToolkit更進一步，提供了細粒度GPU分析：在NVIDIA GPU上，它可以對GPU本身執行PC採樣。自Maxwell以來的NVIDIA硬件可以在執行期間週期性地對warp的程序計數器進行採樣。HPCToolkit通過CUPTI利用這一點來收集GPU指令地址的統計分析，這些地址稍後映射回源代碼行和函數（HPCToolkit對CUDA CUBIN文件進行二進制分析以恢復函數名和行映射）。這產生了GPU代碼的層次分析，類似於CPU採樣如何識別源級別的熱點。（在AMD GPU上，由於缺乏硬件支持，目前無法進行這種細粒度採樣，因此HPCToolkit在那裡只追蹤內核級計時。）該工具還可以通過包裝這些API來追蹤GPU內存分配調用和其他API使用情況。HPCToolkit收集的數據存儲在一個結構化格式中（包含二進制性能數據文件的實驗目錄）。可視化通過HPCToolkit的專用查看器完成：HPC‐Viewer用於聚合分析，HPC‐TraceViewer用於時間線。該設計強調事後分析——數據以低干擾方式收集，然後分析以產生調用路徑分析、追蹤和分析的混合。HPCToolkit的開放設計允許添加對新平臺的支持（最近版本添加了Intel oneAPI Level0甚至OpenMP卸載追蹤）。它的優勢在於將GPU工作關聯回CPU上下文（重建GPU調用上下文樹）並以供應商無關的方式進行（例如，將warp和wavefront統一呈現為抽象線程）。一個限制是配置和處理跟蹤可能很複雜，細粒度GPU採樣（特別是在NVIDIA上）可能會擾亂執行（早期CUDA版本將啟用PC採樣的內核序列化，導致開銷）。儘管如此，HPCToolkit展示了混合方法：採樣+追蹤，大量使用供應商接口但也使用靜態分析將性能指標歸因到代碼。

    基於 eBPF 的 GPU 性能追蹤

    eGPU 和 bpftime 是最近合併的兩個開源項目，展示了利用 Linux eBPF 技術進行真正的零插樁 GPU 性能監控的新方式。與傳統工具通常需要顯式修改目標應用程序、重新編譯，或依賴供應商 SDK（如 NVIDIA Nsight）不同，這套新方案通過操作系統級的動態追蹤，在不修改目標程序二進制的情況下，實現了 GPU 執行階段的實時監控。在 CPU 一端，bpftime 使用 eBPF uprobes（用戶態探針）動態附加到 NVIDIA CUDA 運行時庫（libcudart.so）中的關鍵 API 上，例如 cudaMalloc、cudaMemcpy、cudaFree 和 cudaLaunchKernel 等，攔截並記錄應用程序調用 CUDA API 的情況，具體可以參考 eBPF 實現 CUDA 事件追蹤。當被鉤住的 CUDA 函數調用觸發時，uprobe 會在 Linux 內核中執行一個極為輕量的 BPF 程序，記錄調用參數（如內存分配大小、數據傳輸尺寸）及精確的 CPU 時間戳。這些數據存入內核的 ring buffer 結構中。

    與 Uprobe 等之前僅限於 CPU 端追蹤的方法相比， eGPU 的創新之處在於它在 GPU 內核端也實現了完全的 eBPF 探針能力。eGPU 將用戶編寫的 BPF 字節碼即時（JIT）翻譯為 NVIDIA GPU 原生指令（PTX），並直接注入到運行中的 CUDA kernel 中，從而實時捕獲 GPU 內部事件（如內核啟動、線程塊調度、事件同步和計算單元執行）。由於這種內核級注入是透明進行的，無需修改 GPU kernel 源碼或二進制文件，它極大地提高了 GPU 內部追蹤的精度，提供亞微秒級別的 GPU 端時間戳，追蹤數據的實時性和精確度遠高於傳統用戶態工具。eGPU 現已合併到 https://github.com/eunomia-bpf/bpftime 中，實現了 CPU 和 GPU 兩端事件的統一聚合與同步，兩者通過高效的內核態 ring buffer 進行合併與關聯，確保追蹤過程中數據和時間戳的一致性和低延遲。從功能定位上看，eGPU 和 bpftime 填補了現有 GPU 性能工具之間的空白：它既不需要開發者插樁代碼或重新編譯，也無需依賴供應商專有工具鏈，卻能夠實時揭示內存使用模式、數據傳輸性能瓶頸、GPU 內核的真實啟動延遲及執行效率。這種高效且真正零侵入性的設計極大簡化了實際部署的複雜性。

    NVIDIA DCGM (數據中心GPU管理器)

    DCGM不是針對單個應用程序的性能分析器，而是一個在集群/節點級別的GPU遙測和監控套件。它的架構是面向服務的：DCGM作為一個後臺主機引擎服務（nv-hostengine）運行，或者可以通過其libdcgm.so API嵌入到管理應用程序中。核心DCGM庫與NVIDIA驅動程序接口交互，收集關於GPU的廣泛指標——包括利用率（SM忙碌%，內存使用情況）、溫度、功耗、時鐘速度、內存錯誤，甚至吞吐量統計如PCIe傳輸字節數。這些指標中的許多來自與nvidia-smi相同的底層計數器（通過NVML，NVIDIA管理庫）。DCGM聚合服務器上所有GPU的這些數據。它可以被配置為定期記錄指標並基於策略觸發警報或應用功率上限。開放核心設計意味著核心庫和API是開源的，而一些診斷模塊仍然是專有的。DCGM的主機引擎可以通過CLI (dcgmi)接受命令或通過DCGM-Exporter提供數據，後者與Kubernetes集成。DCGM-Exporter提供一個HTTP端點，持續以Prometheus格式導出GPU指標，允許輕鬆抓取並在Grafana儀表板中可視化。這使DCGM非常適合在容器化環境中進行長期運行監控。在內部追蹤方面，DCGM主要使用驅動程序計數器輪詢和某些健康事件的事件回調（如雙位ECC錯誤）。它不是關於追蹤單個內核啟動，而是關於隨時間聚合的性能和健康。例如，DCGM可以報告作業的平均SM佔用率或內存帶寬，但不能報告哪個函數導致了緩存未命中。它的操作粒度比Nsight或HPCToolkit粗糙——通常以秒為時間尺度——並且設計為具有非常低的開銷（"作業運行時低開銷、非侵入性健康監控"）。在安全方面，DCGM可以以有限的權限運行：默認情況下，可能洩露詳細信息的GPU性能計數器被限制為管理員，但配置（如設置NVreg_RestrictProfilingToAdminUsers=0）可以允許非root DCGM使用。總之，DCGM的架構服務於系統管理員：它為跨節點的GPU指標收集提供了統一的API和服務，與集群管理器和雲監控的集成點。它通過專注於全局GPU行為和健康而不是特定於代碼的性能事件來補充每個應用程序的性能分析器。

    TAU (調優和分析工具)

    TAU是一個可移植的性能分析/追蹤工具包，在HPC中廣泛使用，它已經發展到支持GPU卸載，以及CPU和網絡追蹤。TAU的架構是模塊化的：它可以使用源代碼級插樁、二進制重寫或攔截包裝器來對應用程序進行插樁，並支持許多編程模型（MPI、OpenMP、Pthreads等）。對於GPU支持，TAU利用現有的性能工具接口：它通過CUPTI支持NVIDIA GPU，通過ROCm的ROCprofiler或roctracer支持AMD GPU，通過Level Zero工具支持Intel GPU。具體來說，TAU的運行時庫可以訂閱CUPTI的回調API來追蹤CUDA內核啟動、內存複製等，類似於HPCToolkit的方法。它還支持MPI工具接口（MPI_T）和Kokkos分析鉤子，將高級並行運行時事件與GPU活動關聯起來。TAU通常通過啟動程序的包裝器（tau_exec）使用，該包裝器可以自動注入插樁。例如，tau_exec -cuda將啟用基於CUPTI的所有CUDA API調用和內核的插樁。TAU為每個函數記錄計時器，因此如果攔截了GPU內核啟動，TAU將記錄在CPU上花費在該啟動調用中的時間以及通過CUPTI的異步活動記錄在GPU上的內核執行時間。該工具還可以追蹤數據傳輸大小和計時（例如cudaMemcpy）。除了顯式插樁外，TAU還支持基於事件的採樣。它可以配置硬件計數器或定時器定期對程序計數器進行採樣，然後使用二進制調試信息（通過libdwarf/BFD的DWARF）將這些樣本映射到源代碼行。這對於不使用函數插樁的代碼分析或捕獲系統級異常很有用。TAU將性能結果存儲在緊湊的二進制格式或數據庫中（它有一個用於數據管理的PerfDMF框架）。可視化可以使用TAU的ParaProf GUI完成（顯示每個函數的指標表、每個線程的時間線、調用圖等），或者通過將追蹤轉換為OTF2等格式以使用Vampir等工具。TAU是可擴展的——用戶可以使用TAU API標記自定義事件或代碼中的階段，這些事件或階段將顯示在性能分析中。類似插件的功能存在於TAU可以相對容易地與新的後端測量源接口（TAU團隊添加了對新GPU甚至OMPT的支持，而不改變面向用戶的API）。TAU的設計理念是通過標準工具接口（CUDA/CUPTI、ROCm工具、MPI PMPI、OpenMP OMPT）儘可能多地攔截，以便它不需要修改目標代碼。這使它成為一個多平臺"膠水"性能分析器，但也意味著TAU在給定平臺上的能力受到該平臺API暴露的限制。例如，TAU可以追蹤在GPU內核和數據移動中花費的時間，但對於NVIDIA內核內部細節，它將依賴於CUPTI指標（TAU可以類似於Nsight Compute收集這些指標，儘管TAU通常專注於時間線和聚合時間而不是每個硬件指標）。總之，TAU的內部架構結合了插樁包裝器（自動插入）和採樣，並在性能數據庫中統一數據。它提供了跨CPU、GPU和MPI的整體視圖，這在應用程序跨越所有這些層的HPC設置中是有價值的。

    (其他工具：除了上述工具外，還有特定供應商的GPU性能分析器，如AMD的Radeon GPU Profiler (RGP)用於低級AMD GPU追蹤，Intel的VTune Profiler和Graphics Performance Analyzers用於Intel GPU，以及研究工具如rocProf（AMD上的ROCm命令行性能分析器）。這些通常遵循類似的模式：例如，RGP使用驅動程序級插樁和GPU著色器性能計數器來生成圖形/計算波的時間線，VTune使用Intel的驅動程序在Intel GPU上追蹤Level0或OpenCL內核。由於篇幅限制，我們重點介紹上述主要工具，它們涵蓋了一系列實現策略。)

    這些工具追蹤的API和運行時

    性能分析工具通過鉤入軟件棧的各個層來實現覆蓋。表1總結了每個工具能夠追蹤的運行時、庫或驅動程序API：

    • CUDA驅動程序/運行時(NVIDIA)： 幾乎所有工具（Nsight Systems/Compute、HPCToolkit、TAU、GPUprobe）都支持CUDA。Nsight和TAU使用CUPTI攔截CUDA調用，HPCToolkit使用CUPTI進行活動，GPUprobe通過uprobes鉤入libcudart。開源的Omnitrace目前不支持CUDA（專注於AMD），而DCGM通過NVML在更高級別監控（它看到整體CUDA使用情況但不是單獨的調用）。
    • HIP/ROCm (AMD)： Omnitrace和TAU通過ROCtracer/ROCprofiler支持AMD的HIP運行時。HPCToolkit也使用ROC-tracer進行AMD GPU內核。這些允許追蹤HIP內核啟動、內存複製等。像Nsight（NVIDIA）這樣的工具不支持AMD API。AMD的RGP和rocProf當然本地針對ROCm/HIP。
    • OpenCL： HPCToolkit有函數包裝器來攔截OpenCL API調用，用於缺乏更好接口的GPU。TAU也支持OpenCL追蹤。Nsight Systems可以在NVIDIA平臺上追蹤OpenCL（如果OpenCL實現通過CUDA驅動程序路由，則通過CUPTI）。Omnitrace可能可以通過其二進制插樁處理AMD上的OpenCL（如果配置為插樁這些調用）。
    • Vulkan/OpenGL（圖形API）： Nsight Systems和NVIDIA工具可以追蹤源自圖形API的GPU工作（在時間線上顯示GPU工作，如Vulkan啟動），但我們的重點是計算。像RGP這樣的工具也針對圖形。一般來說，以HPC為中心的工具（HPCToolkit、TAU）默認不追蹤圖形API。
    • Intel oneAPI Level Zero / DPC++： HPCToolkit和TAU已經添加了對Intel GPU卸載的支持。HPCToolkit包裝了Level Zero（oneAPI）API以捕獲內核提交。TAU通過OMPT（OpenMP卸載）接口和Level Zero攔截器支持oneAPI。Intel的VTune也使用驅動程序來追蹤這些，但第三方支持正在興起。
    • 驅動程序級鉤子： 一些工具在驅動程序級別集成：DCGM通過NVML與GPU驅動程序接口以獲取指標，可能直接與內核驅動程序交互以處理節流或健康事件。大多數單個操作的追蹤是在用戶API級別完成的（第三方的驅動程序級插樁很少見，因為GPU驅動程序是專有的閉源，除了AMD的開放驅動程序，ROCtracer可以插入其中）。

    總結來說，NVIDIA的CUPTI是Nsight、HPCToolkit、TAU（以前還有nvprof、Visual Profiler）用來在驅動程序API級別追蹤CUDA並收集計數器的常見接口。AMD的ROCm工具（rocTracer/rocProfiler）對HIP/HSA起著類似的作用。Intel的Level Zero更新；HPCToolkit/TAU中已有支持。這些工具也覆蓋了CPU線程庫（pthreads、通過OMPT的OpenMP、通過PMPI/MPI_T的MPI），以將CPU端階段與GPU活動相關聯。

    CPU與GPU的追蹤及事件關聯

    這些性能分析器的一個重要方面是它們是捕獲CPU端的事件，GPU端的事件，還是兩者都有——以及它們如何合併這些時間線。CPU端追蹤通常涉及記錄應用程序線程何時調用某些API或某些函數何時執行。例如，基於插樁的工具如TAU或Omnitrace會在CPU上調用CUDA內核啟動函數時記錄時間戳。基於採樣的工具如Nsight Systems或HPCToolkit也記錄CPU端樣本（可以指示CPU何時忙碌或空閒）。GPU端追蹤意味著捕獲在GPU設備上發生的事件，如GPU上內核的實際執行間隔，或其他GPU引擎活動（GPU引擎上的內存複製等）。

    大多數工具依賴於供應商支持來獲取GPU端事件計時。例如，NVIDIA上的CUPTI提供內核在GPU上的開始和停止時間戳，Nsight、HPCToolkit和TAU都使用這些信息。類似地，在AMD上，ROCm的活動回調提供GPU內核持續時間。通過收集這些，工具可以繪製實際GPU利用率時間線。GPU硬件通常有一個單獨的時鐘域，但性能分析接口確保時間戳可以轉換為主機時鐘（通常通過在性能分析開始時採樣共同時鐘）。

    關聯然後通過按時間合併CPU和GPU事件流來實現。Nsight Systems在其時間線中做到這一點：可以看到CPU線程啟動一個內核，然後稍後（在同一時間線上）看到GPU活動發生，通過時間戳對齊。HPCToolkit採用不同的方法，通過調用上下文進行關聯：它記錄特定的CPU調用路徑啟動了內核X，並在分析中將內核的GPU時間歸因於該調用路徑，有效地將GPU時間鏈接到CPU調用上下文樹中。這回答了"哪個CPU函數導致了這個GPU工作，它花了多長時間？"這樣的問題。TAU同樣將GPU內核時間歸因於啟動它的CPU代碼區域（具有像TAU_CALLSITE這樣的功能來精確定位源代碼行）。

    處理上下文切換和併發是另一個挑戰。Nsight Systems明確地通過perf或內核跟蹤點追蹤CPU上的上下文切換事件，因此它可以顯示哪個線程正在運行與被搶佔。在與GPU事件關聯時，工具必須考慮GPU內核異步運行的事實：例如，CPU可能將內核排隊並繼續執行，而GPU稍後執行它。性能分析器通常包括流同步信息，以便它們可以顯示在CPU調度之後仍在進行的GPU工作。

    如果多個CPU線程向多個GPU流啟動工作，關聯確保正確的匹配。唯一ID（如CUDA流ID或HIP隊列ID）在內部用於標記事件。例如，CUPTI將報告帶有ID的內核啟動，該ID對應於特定的CPU線程和流，使工具能夠將其與CPU端啟動API調用記錄匹配。

    總之，高級性能分析器追蹤CPU事件（函數調用、線程調度等）和GPU事件（內核執行間隔、設備內存傳輸）。它們通過時間和元數據對齊這些事件，實現一個連貫的視圖。這對於識別流水線延遲至關重要（例如，如果CPU正在等待GPU或反之亦然）。沒有GPU端數據，人們可能只知道CPU何時啟動了內核，而不知道它何時在GPU上完成。相反，僅GPU的追蹤將缺乏CPU在做什麼的上下文。因此，所有被審查的工具使用某種形式的組合追蹤：例如，HPCToolkit的分析顯示組合的CPU+GPU調用路徑，而Nsight Systems使用覆蓋CPU核心和GPU時間線的時間線並行顯示。確保時鐘同步（CUPTI處理CUDA的這一點）和處理異步性是它們實現的關鍵部分。

    插樁與採樣：數據收集策略

    性能分析工具通常採用兩種策略中的一種（或混合）來收集性能數據：插樁（事件追蹤）或統計採樣。每種策略對開銷、準確性和侵入性都有影響。

    • 基於插樁的性能分析： 這涉及插入鉤子或探針，以記錄感興趣的事件每次發生時。例如，用開始/停止計時器包裝函數（如TAU所做的），或使用在每次內核啟動時觸發的CUPTI回調。插樁可以在編譯時（在源代碼或二進制文件中插入代碼）、運行時注入（使用LD_PRELOAD攔截庫調用，或像Omnitrace那樣進行動態二進制插樁）或在操作系統級別（使用GPUprobe所做的kprobes/uprobes）完成。優勢是完整的信息：記錄每個事件，提供確切的計數和計時。缺點是如果事件頻繁，開銷可能會很高。例如，對細粒度應用程序中的每個函數調用進行插樁可能會顯著減慢它。像TAU和Omnitrace這樣的工具使用插樁來獲取詳細的追蹤（Omnitrace通過二進制插樁，TAU通過包裝器庫和基於編譯器的插樁）。GPU驅動程序API通常通過官方回調接口（CUPTI、ROCtracer）進行插樁，以追蹤GPU事件而不修改供應商代碼。插樁還可以使用動態運行時方法：例如，LD_PRELOAD用於通過在加載時覆蓋符號來攔截malloc或CUDA調用；二進制重寫可以永久地在代碼中添加探針；而uprobes/kprobes允許在函數入口處插入斷點（GPUprobe使用uprobes在運行時附加到cudaLaunchKernel等）。每種方法在靈活性與性能之間有權衡。

    • 基於採樣的性能分析： 這種技術在間隔（基於時間或事件）而不是記錄每個事件時收集信息。對於CPU，這通常意味著使用硬件計時器或性能計數器溢出中斷定期採樣程序計數器（PC）和調用棧。對於GPU，採樣可能意味著定期查詢利用率，或者在NVIDIA的情況下，使用GPU上的PC採樣，如前所述。Nsight Systems使用定時採樣來採樣CPU線程（例如，以一定間隔捕獲堆棧跟蹤，以統計推斷熱點代碼）。HPCToolkit嚴重依賴採樣來分析CPU（並可選擇使用GPU PC採樣進行細粒度GPU分析）。採樣的優勢是開銷低得多——例如，每秒捕獲1000個樣本幾乎不會導致減速，但提供了統計覆蓋，顯示時間花在哪裡。它還自動過濾掉非常快的事件（如果一個函數執行100ns，它可能永遠不會被採樣，從而有效地專注於主要成本）。缺點是精度降低：你可能會錯過不頻繁的事件或引入採樣誤差。此外，對於事件計時（如精確的內核持續時間），採樣不合適——它更適合聚合指標，如"哪些代碼平均消耗了多少週期"。

    • 混合方法： 許多工具結合了兩者。例如，Nsight Systems對GPU事件進行插樁（以精確計時內核），但對CPU活動進行採樣（以降低開銷）。HPCToolkit在粗粒度級別（GPU內核）進行插樁，並對其他一切使用採樣。Omnitrace對函數進入/退出進行插樁，並對調用棧進行採樣。這種混合策略允許捕獲關鍵事件，同時保持開銷可控。

    在現代GPU性能分析中，事件追蹤通常用於GPU操作，因為GPU工作通常是稀疏的（內核、內存複製）並由運行時API明確定義——記錄每個內核啟動是可行的。同時，採樣通常用於CPU計算或長時間GPU內核內部，以瞭解其內部行為（如內核內的PC採樣，本質上是在GPU執行中採樣事件）。一個特殊情況是硬件計數器採樣：一些工具設置硬件PMU來採樣特定事件，例如計算緩存未命中並在溢出時採樣指令地址（這合併了兩個世界：設置計數器的插樁，採樣來捕獲事件）。

    策略總結： 如果開發者需要精確的事件時間線和計數，首選插樁（用於追蹤工具、時間線可視化等）。如果需要對大型應用程序進行低開銷性能分析以查找熱點，首選採樣（用於HPC性能分析器、統計性能分析器）。許多工具提供兩種模式。實現必須仔細管理插樁的啟用/禁用（例如，支持選擇性插樁——Omnitrace允許配置要插樁的函數，TAU允許通過標誌切換MPI、I/O、GPU的插樁）。這有助於針對分析並減少數據量。

    硬件性能計數器（PMU）的使用

    硬件性能監控單元（PMU）對於在CPU和GPU上收集無法通過高級計時獲得的低級指標（如指令計數、緩存未命中、內存吞吐量等）至關重要。

    CPU PMU： 大多數CPU通過Linux perf等接口暴露計數器。像HPCToolkit和TAU這樣的工具可以使用PAPI庫來配置CPU計數器（週期、緩存未命中、浮點運算等）並在溢出時進行採樣。例如，HPCToolkit的命令hpcrun -e PAPI_TOT_CYC@500000 -e PAPI_L2_TCM@200000將在總週期和L2緩存未命中達到特定計數後進行採樣。通過使用這些計數器作為採樣觸發器，工具將硬件事件歸因到代碼位置。TAU也與PAPI集成，如果進行了插樁，它可以記錄每個函數調用的計數器（在每個區域內累加計數）。在內核級分析（如操作系統調度）中，也可能通過ftrace或BPF使用CPU PMU，但這在面向用戶的性能分析器中不太常見。

    GPU PMU： 現代GPU有廣泛的性能計數器（NVIDIA上每個流式多處理器，AMD上每個計算單元）。對這些的訪問是通過供應商庫實現的：

    • NVIDIA提供CUPTI/Event和Metric API，允許工具列出可用的計數器（例如，"dram_read_transactions"、"active_warps"）並讀取它們。像Nsight Compute這樣的工具編程這些計數器並在內核執行後讀取它們。一些計數器可以在內核之後讀取（給出該內核的聚合計數），使用CUDA的分析模式。其他可能會持續採樣（NVIDIA支持"流式性能監視器"模式進行持續收集，但這通常是內部的）。
    • AMD通過ROCprofiler或GPUPerfAPI（GPAPI）提供類似的接口來訪問性能計數器。Radeon GPU Profiler（RGP）和rocprof可以收集AMD GPU的計數器，如wavefront佔用率、緩存命中等。Omnitrace可能在底層使用ROCprofiler（因為它是為AMD構建的）來獲取計數器，除了跟蹤回調。
    • Intel GPU（Xe）通過VTune或Metrics Discovery API暴露計數器，HPC工具才剛開始支持這些。HPCToolkit提到通過Level Zero以有限方式支持Intel GPU指標（可能鏈接到Intel的GT-Pin或使用oneAPI VTune後端）。

    內核內計數器和PMU： 一些性能分析方法也使用操作系統級計數器。例如，Linux有GPU調度器事件的跟蹤點（在一些開源驅動程序上），可用於跟蹤GPU引擎上的上下文切換。此外，NVIDIA的驅動程序跟蹤諸如內存頁遷移、NVLink使用等，DCGM可以檢索這些信息。DCGM使用一部分計數器來監控健康狀況（如內存ECC計數）和吞吐量（PCIe字節），這些通常不向應用性能分析器暴露。

    PMU數據使用： 原始計數器值通常需要後處理才有意義：

    • 派生指標： 許多工具提供計算比率或百分比。例如，SM佔用率派生自"活動warp"與"理論最大warp"計數器的比較。緩存命中率派生自緩存命中和未命中計數器。Nsight Compute明確計算這些指標，甚至提供指導性分析規則（例如，如果某個停滯原因計數器很高，就建議優化）。HPCToolkit以中立方式呈現原始指標（計數或百分比），但不專注於指導性提示。
    • 採樣與聚合： 當計數器被採樣（如設置計數器觸發中斷）時，你得到基於樣本的歸因（如"20個L2未命中樣本發生在函數X中"）。當計數器按內核聚合（如Nsight Compute所做）時，你得到該內核的確切計數，但必須歸因於整個內核調用。一些工具可能使用PC採樣結合計數器在內核內按源代碼行進行細分（例如，將PC樣本與"已發出指令"計數指標相關聯，以估計代碼每個部分執行了多少指令）。

    開銷： 訪問GPU計數器通常需要對GPU性能監控硬件進行獨佔控制，這就是為什麼一次只能運行一個性能分析會話。在NVIDIA上，如果一個計數器分析器（Nsight Compute或CUPTI指標）正在運行，另一個就不能運行，默認情況下只有特權用戶可以使用計數器，因為可能存在旁路洩漏。AMD的ROCm可能允許更多併發使用，但仍有開銷。工具必須錯開計數器讀取，以避免擾亂GPU流水線（因此Nsight Compute的內核重放確保原始執行不會因一次讀取太多計數器而減慢）。

    總之，PMU是低級指標的基礎。工具實現者通過供應商API（CUPTI、ROCprofiler等）與這些交互，這些API抽象了直接寄存器操作。在某些情況下，開源工具已經逆向工程了部分內容：例如，通過未記錄的perf事件讀取Nvidia GPU性能計數器——但通常由於複雜性，使用官方API是常態。PMU的使用使得可以深入瞭解內存帶寬（通過計算傳輸的字節數）、執行效率（已發出與已完成指令）、停滯（硬件可以在Nvidia上自Volta以來按類別計數停滯原因）等。這些指標大大豐富了性能分析器的輸出，超越簡單的計時，但代價是更復雜的數據收集。

    插樁的鉤子和技術

    為了實現插樁，工具可能鉤入軟件棧的不同層。以下是常見技術：

    • 用戶模式API包裝： 許多工具創建包裝庫，攔截對標準API的調用。例子包括TAU對MPI的攔截（通過PMPI），或包裝CUDA運行時調用。這可以通過提供定義相同符號的庫（例如，一個在記錄後調用真實函數的cudaLaunchKernel）並使用LD_PRELOAD或鏈接順序確保使用包裝器來完成。HPCToolkit的基礎設施有OpenCL和Level Zero的函數包裝器，可能以這種方式操作。這種方法直接且不需要特殊權限，但你必須為每個感興趣的函數實現一個包裝器。它用於高級事件（例如，記錄內核已啟動，然後調用實際啟動）。

    • 編譯器/源代碼插樁： TAU可以插樁源代碼或使用編譯器標誌（如使用-finstrument-functions或使用Clang/OMPT進行OpenMP）。這將探針編譯到程序中。優勢在於豐富的上下文（你可以在循環或函數入口處插樁，計時器開銷最小），但需要重新編譯或至少添加額外的編譯步驟。

    • 動態二進制插樁（DBI）： 像Omnitrace這樣的工具執行DBI，意味著它們在運行時或預先將插樁注入二進制文件，無需源代碼。DBI框架包括Dyninst、Intel PIN或DynamoRIO。Omnitrace被描述為對函數進行動態插樁。這很強大，因為它可以插樁即使是第三方庫代碼（源代碼不可用）並可以動態配置。代價是複雜性和一些開銷，因為代碼修補和在DBI環境下運行。

    • 內核探針（kprobes）和eBPF： 對於系統範圍或內核級事件，性能分析器可以使用kprobes（插樁內核函數）或跟蹤點。例如，要測量GPU驅動程序事件，可以在GPU驅動程序中插入kprobes，如果你知道符號（在調試之外不常見）。更實際地，eBPF被GPUprobe用來附加到用戶級函數（uprobes），也可以附加到內核跟蹤點（如調度或GPU中斷）。eBPF的優勢是它是動態的（無需應用程序重建）並且在生產中運行是安全的（在內核中沙盒化）。我們看到GPUprobe使用uprobes；類似地，可以將kprobes附加到，例如，GPU調度器的作業提交函數，以知道內核何時在硬件上調度。除了GPUprobe外，很少有性能分析工具目前使用eBPF，但這種技術正在引起人們對內核和用戶事件低開銷插樁的興趣。例如，可以想象一個基於eBPF的性能分析器，通過每隔幾毫秒輪詢設備文件來採樣GPU利用率，或跟蹤影響GPU的操作系統事件（如GPU中斷、DMA完成事件）。

    • 驅動程序/內核插樁鉤子： 一些供應商允許在驅動程序級別插入鉤子。NVIDIA的CUPTI本質上在CUDA驅動程序內部註冊鉤子——NVIDIA為性能分析器構建了這個。AMD的ROCtracer通過與ROCm驅動程序棧接口類似地做到這一點。如果源代碼可用（AMD的運行時是開源的），甚至可以修改或擴展它以添加自定義探針，但通常提供的鉤子就足夠了。在CPU上，操作系統提供跟蹤點（如上下文切換事件、系統調用事件），Nsight Systems等工具用它們來跟蹤調度。這些本質上是內核中的插樁點（例如，sched:sched_switch跟蹤點）。工具可能通過perf子系統或ftrace接口啟用這些。

    • GPU指令注入： 在某些情況下，插樁可以插入到GPU代碼本身。這在商業工具中不常見（由於改變行為的風險），但研究工具或某些調試模式會這樣做。例如，可以修改PTX（CUDA彙編）在某些點調用計數器增量。NVIDIA較舊的性能分析（CUPTI PC採樣）是比顯式插樁更好的方法，但NVIDIA可以在warp-trap指令處進行插樁。AMD的著色器性能分析可能在代碼中插入"wave時間戳"。然而，通常供應商避免修改用戶內核進行性能分析，而是在特殊模式下運行它們（如單warp重放或序列化執行以進行分析）。

    • Uprobe/Uretprobe用於參數/返回： 如GPUprobe所示，有時需要同時插樁函數的入口和出口，以獲取參數和返回值。Uretprobes捕獲函數返回，但由於寄存器可能被破壞，使用入口uprobe（存儲參數）和返回探針的組合。這種技術需要測量諸如分配大小（入口參數）和分配指針（退出時返回）等內容，而不改變函數。

    • 事件緩衝區和異步日誌記錄： 插樁通常將數據記錄到緩衝區以最小化干擾。例如，CUPTI將活動記錄寫入緩衝區，性能分析器稍後讀取。eBPF將事件寫入BPF環形緩衝區或映射，由用戶空間異步消費。這種解耦對性能至關重要：插樁函數觸發快速日誌寫入（例如，只在無鎖隊列中放置事件）然後繼續，而另一個線程或進程處理諸如寫入磁盤或網絡等重任務。

    總體而言，實施插樁是關於仔細選擇在哪裡攔截（用戶API、庫或內核）、如何注入探針（源代碼vs二進制vs動態）以及如何處理數據（立即打印vs緩衝）。我們討論的工具說明了這些選擇：例如，TAU主要使用用戶API包裝，Omnitrace使用DBI，GPUprobe使用內核uprobes，Nsight依賴驅動程序提供的鉤子，HPCToolkit使用驅動程序鉤子和自己的包裝器的混合。

    GPU指令級追蹤技術

    在GPU上進行指令級或warp級別的性能分析極具挑戰性，因為操作量龐大且可觀察性有限。然而，存在一些方法：

    • GPU PC採樣： 如前所述，NVIDIA GPU支持在每個SM上定期採樣程序計數器。這類似於CPU PC採樣，提供關於哪些指令（或源代碼行）在GPU上頻繁執行的統計視圖。HPCToolkit使用這一點將時間或週期歸因到GPU內核中的代碼行。CUPTI PC採樣機制還可以歸因採樣warp的停滯原因（例如，warp是否因內存、執行依賴等而停滯）——提供關於為何性能損失的洞察。這有效地提供了指令級洞察（代碼的哪些部分是熱點，它們引起什麼停滯）。開銷可能不小，早期實現會序列化執行，但較新的GPU通過將樣本收集卸載到硬件緩衝區更有效地處理PC採樣。
    • 硬件流水線統計： 與其追蹤每條指令，GPU有計數器來統計"每週期發出的warp指令數"或"因X原因停滯的週期數"等。Nsight Compute讀取這些來生成指令流水線利用率分析（例如，顯示IPC、發出停滯細分）。雖然不是逐條指令的追蹤，但它提供了指令級別類別的聚合視圖。其中一些計數器實質上將warp的週期分類（內存、計算等），這幾乎就像是隨時間追蹤流水線氣泡的原因。
    • Wavefront/warp追蹤調試模式： 在調試上下文中，GPU可以被置於模式中，讓單個warp運行到完成或記錄特定事件。AMD的GPU PerfStudio有低級模式，NVIDIA有如Nsight Graphics這樣的工具，可以捕獲每個繪製調用的計時直至著色器指令（用於圖形）。但對於通用計算，由於開銷，很少使用這種指令追蹤。
    • 逆向工程和未記錄的方法： 開源開發者有時會逆向工程著色器ISA以獲取指令信息。例如，HPCToolkit的開發者編寫了自己的CUBIN分析器，將指令地址映射到行號，因為NVIDIA不提供SASS的源代碼行映射。類似地，在AMD上，可能解析代碼對象（其ISA）以與HSAIL或源代碼關聯。這些是離線分析，但對於指令級性能分析至關重要，因為工具必須將性能指標歸因到單個指令或行。如果沒有供應商文檔，這涉及大量自定義工具開發。

    總之，GPU上的指令級追蹤是通過智能採樣和計數器而非逐事件追蹤（這會使任何系統不堪重負）。PC採樣和專用計數器的組合提供了指令追蹤的近似，足以突出低效指令或代碼中的停滯部分。這種詳細程度通常只在優化特定內核時需要（因此使用Nsight Compute或學術項目如GPU性能模擬器等工具）。大多數通用性能分析器不會輸出執行的每條指令的日誌（那更屬於模擬器或非常特殊的調試模式的領域）。

    數據收集、傳輸和存儲

    性能分析器收集大量數據——它們如何管理這些數據與收集本身一樣重要。關鍵考慮因素是：數據如何從GPU移動到主機，如何緩衝，使用什麼文件格式，以及用戶最終如何訪問它。

    • 從GPU到CPU的數據傳輸： 收集GPU性能數據（計數器或跟蹤）時，數據必須傳輸到主機。例如，CUPTI的Activity API在緩衝區中累積記錄，然後通過驅動程序回調將它們刷新到主機內存。這通常在內核完成後或緩衝區填滿時發生。對於連續指標，DCGM或其他工具通過驅動程序調用定期查詢GPU（在底層通過PCIe讀取寄存器）。數據傳輸的開銷通過批處理減輕：性能分析器使用大緩衝區，只偶爾中斷GPU以排出數據。一些高級用法可能會固定緩衝區，讓GPU通過DMA輸出數據（NVIDIA的NVPW流式計數器做類似的事情）。但細節通常由供應商庫抽象。

    • 緩衝和流式傳輸： 大多數工具實現雙緩衝或隊列，使數據收集和寫入磁盤不會阻塞應用程序。例如，HPCToolkit將GPU事件記錄到內存緩衝區，在運行後寫入文件。Nsight Systems增量寫入內存映射文件（如果連接，甚至可以流式傳輸到UI）。GPUprobe使用BPF隊列，用戶空間每隔幾秒讀取一次。實時流式傳輸跟蹤數據很棘手，因為數據量大，但一些工具（如某些調試模式或Intel GPA）通過將事件通過套接字發送到GUI允許實時查看。在HPC中，通常數據被寫入本地存儲以進行事後分析，因為數據量很大（多GB跟蹤）。

    • 文件格式： 有多種格式：

    • 專有二進制：Nsight Systems和Compute使用自己的二進制格式（Nsight Systems中的.nsys-rep實際上是SQLite數據庫；Nsight Compute的.ncu-rep是帶有部分的結構化二進制）。這些針對它們的GUI進行優化，不打算手動編輯。

    • 開放跟蹤格式：一些開源工具使用標準格式如OTF2（開放跟蹤格式）或CTF。例如，TAU可以導出為OTF2。這些格式設計用於合併HPC中多個等級的跟蹤。
    • Perfetto/Chrome JSON：Perfetto格式（protobuf跟蹤）或較舊的Chrome Trace Event格式（JSON）被多個工具使用，因為Chrome的跟蹤基礎設施是事實上的標準。例如，PyTorch的性能分析器輸出Chrome JSON跟蹤，TensorBoard或chrome://tracing可以顯示。Omnitrace寫入Perfetto .proto文件，可在Perfetto UI中查看。GPUprobe不產生完整時間線，但可以擴展以輸出事件的Chrome跟蹤JSON。
    • 純文本/CSV：許多工具也生成人類可讀的摘要報告。Nsight Compute CLI可以輸出每個內核的CSV指標。HPCToolkit生成頂級熱點的文本報告。DCGM的dcgmi可以將當前指標打印到控制檯，DCGM導出器為Prometheus輸出文本。

    • 數據庫：一些工具將數據存儲在SQL或自定義數據庫中。如前所述，Nsight Systems在底層使用SQLite；TAU的PerfDMF歷史上使用數據庫存儲性能分析數據以供查詢。使用數據庫可以便於事後查詢特定指標。

    • 導出路徑和遙測：工具在如何檢索數據方面有所不同。

    • 基於文件的工作流：例如，運行nsys profile ...生成稍後打開的文件；運行hpcrun然後hpcstruct/hpcprof生成分析數據庫。

    • 實時UI：例如，Nsight Systems也可以與附加到遠程應用程序的GUI一起運行，流式傳輸數據。Intel VTune可以附加到正在運行的進程，定期在UI中更新統計信息。
    • Web儀表板：一些現代性能分析器有Web界面。例如，NVIDIA在其雲中推出了Web版Nsight Systems，Omnitrace結果可以輕鬆加載到Perfetto網頁查看器中。DCGM的Kubernetes集成專門用於儀表板：DCGM導出器提供Prometheus數據，在Grafana或其他工具中可視化。
    • 與TensorBoard集成：針對ML的工具（如PyTorch的Kineto或TensorFlow的性能分析器）導出TensorBoard性能分析插件可以顯示的數據。這些通常使用Chrome跟蹤格式。例如，使用Kineto的PyTorch可以捕獲CUDA內核時間線並在TensorBoard中顯示，有效地提供類似Nsight的視圖，但在ML工具環境中。底層，Kineto使用CUPTI（與Nsight Systems類似的數據），但轉換為Chrome格式。

    • 自定義遙測API：少數工具允許程序化訪問。DCGM有C和Python API，所以你可以從應用程序或腳本中查詢指標。CUPTI提供了一種程序化方式來開始/停止追蹤並獲取記錄（所以可以將CUPTI嵌入到應用程序中以收集自己的跟蹤）。一些HPC監控系統通過鉤入這些API集成性能分析。

    • 數據量和減少：單次運行可能產生巨大的數據（每個內核啟動的跟蹤等）。工具實現過濾和詳細級別。Nsight Systems有選項限制收集（例如，只跟蹤CUDA，如果不需要則忽略操作系統調度）。HPCToolkit可以配置為只跟蹤GPU而不收集CPU樣本等。它們還有選項包括/排除特定內核或API調用。這很重要，因為在長時間運行中寫出每個事件可能不可行。一些工具，如Score-P（在大規模場景中與TAU一起使用），允許在性能分析（聚合計數）和跟蹤（詳細事件日誌）模式之間切換，因為完整跟蹤超過一定點就不可擴展。

    總結，這些工具中的數據處理涉及事件的仔細緩衝，使用高效的文件格式（通常是二進制或壓縮的），並提供直接可視化或導出到其他分析框架的方式。趨勢是標準化使用Perfetto/Chromium trace格式用於時間線數據，JSON/CSV用於摘要指標，以便於集成。像Omnitrace這樣的工具明確擁抱網頁可視化，生成Perfetto跟蹤，而HPC工具保持更加自定義但提供轉換工具。在集群監控中，流式導出（通過DCGM導出器使用Prometheus）對實時可觀察性至關重要。因此，我們看到事後分析工作流（HPC，桌面性能分析）和實時監控（數據中心，雲）根據用例的不同而共存。

    可視化和分析界面

    性能數據的呈現方式對於獲取洞察至關重要。不同的可視化幫助回答不同的問題：

    • 時間線圖： 這些由Nsight Systems、Chrome/Perfetto跟蹤查看器、HPCToolkit的TraceViewer等提供。時間線在水平軸上顯示時間，在垂直軸上顯示不同的活動（線程、GPU流、網絡傳輸）。這對於識別併發問題和空閒間隙非常出色。例如，可以看到GPU在CPU執行某些操作時是否空閒（表明潛在的CPU瓶頸或排隊工作不足），或者CPU線程是否空閒等待GPU（可能是同步延遲）。在時間線中，你可能會看到重疊的矩形，其中一個內核在另一個CPU線程運行時執行——這是良好的利用率——相對於大的間隙，這表示流水線停滯。依賴關係或事件鏈接可以被繪製（Nsight顯示從CPU啟動事件到它觸發的GPU內核執行事件的箭頭），所以你可以看到關係和任何排隊延遲。時間線還可以顯示CPU上的上下文切換（上下文切換前後使用不同的線程顏色），幫助識別是否有太多上下文切換影響性能。總體而言，時間線可視化提供了流水線瓶頸（例如，GPU等待來自磁盤/CPU的數據）、重疊計算/通信和跨設備的負載平衡等洞察。

    • 火焰圖/調用棧圖： 火焰圖通常由採樣數據產生——它可視化隨時間或聚合的調用棧分析。HPCToolkit的HPCViewer和TAU的ParaProf可以顯示類似火焰圖的內容：基本上，哪些函數調用了哪些函數，以及每個函數花費了多少時間（通常繪製為堆疊條或"火焰"，寬度對應於時間）。這有助於根據調用上下文識別熱點：例如，你可以看到函數foo()佔用了30%的時間，主要是在從main()調用時，而不是從init()調用時。它還可以暴露遞歸或昂貴的調用鏈。在GPU上下文中，HPCToolkit可以顯示GPU內核執行的火焰圖，歸因於啟動它們的CPU調用路徑——這是獨特的，因為它將設備時間連接到火焰圖中。火焰圖（如Brendan Gregg的flamegraph工具生成的）通常是樣本數據的靜態可視化；許多性能工程師使用它們來快速瞭解時間去向。

    • 有向無環圖（依賴圖）： 一些工具（尤其是在並行運行時上下文中）可以可視化任務圖或依賴關係。例如，在GPU操作的流水線中，圖視圖可能顯示內核A和B並行運行，然後流入C。NVIDIA的Nsight Compute不這樣做，但Nsight Systems通過時間線隱式顯示依賴關係。其他分析工具可能重建計算和數據移動的圖（這更為小眾，通常手動完成或通過自定義分析，但不是列出工具的主要功能，除了可能作為可視化異步依賴關係的箭頭部分）。

    • 散點圖： 當你有許多類似事件並想查看分佈時，這些很有用。例如，繪製內核執行時間與內核啟動索引的關係可以顯示後面的內核是否變慢（可能由於熱節流或爭用）。散點圖還可能顯示兩個指標之間的相關性——例如，可以繪製內核的已實現佔用率與執行時間的關係，以查看低佔用率是否與較長的運行時間相關。工具通常不在其UI中包含散點圖，但用戶導出數據進行此類分析。一個例外是一些研究/專業工具，它們允許在內核之間繪製一個指標與另一個指標的關係。

    • 熱圖： 熱圖可能用於顯示，例如，GPU單元利用率的時間線熱圖（一些圖形工具顯示每個SM的利用率隨時間變化的熱圖）。另一個用途是可視化內存訪問模式——例如，GPU內存地址與時間。這些是專門的，通常不在通用性能分析器中找到，但可以生成，例如，緩存未命中率隨時間片段的熱圖，以發現計算階段。在性能分析文獻中，"GPU利用率熱圖"可能指的是顯示每個引擎隨時間的忙碌程度。

    • 指標儀表板： 一些可視化僅僅是指標的表格或圖表。Nsight Compute的GUI顯示指標表，並可能以紅色突出顯示有問題的指標。DCGM與Grafana將顯示指標隨時間變化的線圖（如GPU溫度或利用率%）。這些有助於監控和趨勢分析（作業是否飽和內存帶寬？GPU利用率是否在某個點下降？）。

    每種可視化提供不同的洞察：

    • 從時間線中，可以觀察到CPU-GPU不同步：例如，CPU啟動內核然後什麼都不做（空閒）直到結果返回——表明CPU可以做其他工作或內核是瓶頸。或者相反：GPU空閒是因為CPU沒有提供足夠的工作（可能是單線程CPU代碼導致GPU飢餓）。這些場景在時間線上明顯表現為大的間隙。
    • 流水線瓶頸：例如，在深度學習中，時間線可能顯示CPU上的數據加載很慢，使GPU等待（常見問題）。或者如果有多個GPU，可能會看到一個GPU提前完成然後在同步點等待——表明負載不平衡。
    • 內存帶寬爭用：如果性能分析器捕獲內存吞吐量，可能會看到它在某些內核運行時達到最大（接近100%利用率），解釋為什麼這些內核不會進一步加速（內存受限）。DCGM和Nsight可以報告PCIe或NVLink使用情況；高使用率可能解釋延遲，如果作業移動大量數據。如果運行多個進程，時間線甚至可能顯示重疊的數據傳輸，這些傳輸使總線飽和。
    • 緩存未命中和停滯：像Nsight Compute這樣的工具列出緩存命中率和停滯原因。它們可能不會可視化它們，但報告有效地突出了內存爭用（例如，高L2未命中率和許多內存停滯週期）。用戶可以從這些指標推斷內存延遲正在影響性能。
    • CPU線程問題：火焰圖或時間線可能顯示過多的上下文切換或鎖爭用（如果插樁）。Nsight Systems可以顯示CPU線程的互斥等待時間，幫助找到CPU上的併發問題，這些問題間接減慢了GPU供給。
    • 依賴圖（如果手動分析）可以突出顯示異步工作中的關鍵路徑——例如，內核可能可以併發運行，但由於可優化的依賴關係而按順序調度。
    • 在GPU代碼上的火焰圖（通過PC採樣）可以揭示內核代碼的哪一部分是熱點。例如，HPCToolkit的GPU PC採樣可能顯示內核中40%的時間花在特定循環（源代碼行X）上，暗示該循環是內存受限或計算密集型，適合優化。

    實際上，許多工具集成了多種視圖。Nsight Systems有時間線，加上放大查看特定時刻每個線程的調用棧的能力。TAU的ParaProf可以顯示分析表和時間線（如果啟用跟蹤）。HPCToolkit有單獨的查看器用於聚合分析（如自上而下的調用樹與指標）和事件時間線（如果需要精細細節）。這種組合很強大：人們可能使用分析找到主要罪魁禍首函數，然後檢查時間線看看它為什麼慢（可能是併發問題），然後使用硬件指標視圖看看它是CPU受限還是內存受限等。

    可擴展性和自定義插樁

    不同工具提供不同程度的可擴展性——即能夠整合新的事件源或定義自定義指標和插件：

    • 用戶標記和註釋： 許多性能分析器允許用戶標記代碼的部分。NVIDIA提供NVTX（NVIDIA工具擴展）——一個開發者可以註釋代碼區域或事件的庫。Nsight Systems將在時間線上顯示這些NVTX範圍（用於標記應用程序的階段很有用）。類似地，對於CPU，有像Intel的ITT（插樁和跟蹤技術）這樣的註釋API，一些工具（如VTune或oneAPI工具）使用；TAU有自己的API（例如，TAU_PROFILE_TIMER_START(name)）。這些不是工具的擴展本身，但它們允許用戶注入工具將記錄和可視化的自定義事件。這對於理解高級階段（如在時間線上的"數據預處理"、"訓練步驟"等）至關重要。

    • 插件架構： 一些工具有模塊化設計，可以添加新模塊。例如，DCGM的診斷是模塊化的——可以添加新的診斷插件（儘管編寫一個可能需要NVIDIA的合作，因為不是完全開源）。HPCToolkit不是真正基於插件的，但由於是開源的，用戶已經添加了功能（比如可以通過為其API編寫新連接器來添加對新GPU的支持）。TAU相當可擴展；它是學術性能工具社區的一部分（與MPI_T、OMPT等標準一致）。如果出現新的運行時（比如新的任務庫），TAU可以為其添加接口。

    • 定義新事件： 在像TAU和HPCToolkit這樣的工具中，你可以通過使用工具的API（對於應用開發者）或由工具維護者為新庫函數添加包裝器來插樁新事件。例如，當OpenACC和OMPT接口出現時，TAU迅速集成了這些，這意味著它們有效地"教會"了TAU處理新事件類型（OpenACC卸載事件、OpenMP運行時事件）。類似地，HPCToolkit添加Level Zero支持是實現新回調處理程序和包裝器的問題。因為HPCToolkit的設計是供應商中立的，添加一個API意味著用另一個連接器擴展其基礎設施。Omnitrace作為AMD研究項目，通過添加CUPTI集成（如果有人實現）可能擴展到支持CUDA——框架已經存在（二進制插樁和Perfetto輸出），它只需要來自NVIDIA的事件源。

    • 數據收集的定製： 一些性能分析器允許腳本或配置來決定收集什麼。例如，Nsight Compute有"部分"和規則——高級用戶可以在Nsight Compute的部分文件中定義自定義指標集甚至自定義公式來派生指標（有一種方式在Nsight中編寫自定義分析規則）。這是一種針對指標的有限形式的可擴展性。類似地，可以選擇要收集哪些計數器（減少開銷）。像rocprof這樣的AMD工具允許用戶通過配置文件指定啟用哪些計數器和哪些API回調。

    • 輸出集成： 可擴展性還意味著數據可以多麼容易地用於其他地方。提供標準格式（JSON、CSV、Prometheus等）的工具實際上是可擴展的，因為它們允許將數據插入到自定義管道中（如自定義ML性能儀表板或自動迴歸測試器）。Omnitrace與Hatchet（這是一個分析庫）的兼容性意味著用戶可以通過編寫Python來過濾或比較分析來擴展分析。TAU有一個接口來合併多次運行的分析，可用於自動化測試和分析。

    • 可擴展性的限制： 值得注意的是，像Nsight Systems/Compute這樣的閉源工具不支持插件——你不能向Nsight添加超出NVIDIA提供的新事件類型。你限於使用NVTX標記進行自定義註釋。相比之下，開源工具（HPCToolkit、TAU、Omnitrace、GPUprobe）允許你修改或擴展它們，但需要編程。例如，GPUprobe可以通過在其源代碼中添加更多BPF探針來擴展追蹤新的CUDA函數甚至其他庫。

    • 腳本和自動化： 一些性能分析框架（尤其是在HPC中）支持自動化性能分析實驗。例如，使用TAU的Python接口或腳本TAU commander在不同運行中收集不同的指標，然後綜合結果。這不是插件，但它表明該工具可以集成到更大的工作流程中（如自動調優循環或持續集成以捕獲性能迴歸）。

    總之，可擴展性範圍從簡單的應用內註釋（讓終端用戶標記事件）到能夠集成新後端（讓工具開發者支持新硬件）。調查的工具顯示，開放框架和HPC工具優先考慮靈活性（因為它們需要針對不斷發展的平臺），而供應商GUI優先考慮在固定範圍內的完善體驗。對於構建新性能分析器的人來說，利用標準（如CUPTI、ROCtracer、OMPT）是一個很好的起點，因為它立即授予對各種事件的支持，並設計工具接受插件模塊或配置文件來獲取新指標可以使其面向未來。

    開銷和侵入性權衡

    性能分析本質上會擾亂目標程序——關鍵是最小化並理解這種開銷。不同工具有不同的影響：

    • 輕量級採樣 – 低開銷： 低頻率採樣（例如，每秒100-1000個樣本）通常產生低於5%的開銷，往往不引人注意。HPCToolkit的CPU採樣屬於這一類別，使其適用於大型HPC作業，在這些作業中即使增加10%的開銷也太多。HPCToolkit明確目標是每個線程每秒幾百個樣本，以保持合理的開銷。類似地，Nsight Systems的CPU採樣設計為非常低的開銷，使用為此優化的操作系統級perf。權衡是你可能不會捕獲非常短暫的函數或獲得精確的計數。

    • 函數插樁 – 中到高開銷： 在每個函數進入/退出或每個CUDA調用上包裝或插入代碼可能會增加顯著的時間，特別是如果這些函數很頻繁。TAU的開銷取決於插樁的粒度：只插樁外部循環或MPI調用成本低，但插樁每個C++內聯函數可能開銷巨大。TAU允許選擇級別（例如，如果試圖減少開銷，你可能不會插樁每個GPU內核啟動，只插樁整體區域）。Omnitrace的動態插樁在啟動時會有一些開銷，以及每個插樁函數調用的運行時開銷（他們試圖最小化它，但它確實存在）。Omnitrace文檔強調將其用於整體執行分析，而不是每個內核的超精細細節（實際上建議如果想深入瞭解單個內核，使用另一個工具——暗示Omnitrace專注於廣泛分析，而非微優化單個內核）。

    • GPU追蹤開銷： 僅通過CUPTI追蹤內核事件開銷很低——每個內核記錄事件幾微秒。如果內核數量眾多（每秒數千個），這可能開始變得重要。CUPTI的活動緩衝通常可以高效處理許多事件。但當你開啟更詳細的GPU分析（如計數器或PC採樣）時，開銷增加。CUPTI的PC採樣可能降低應用程序性能，尤其是在舊GPU中，它阻止了內核的重疊。工具通常對此發出警告；例如，Nsight Compute重放內核，因為試圖在一次運行中收集所有指標會極大減慢內核或由於計數器限制而不可能。所以Nsight Compute是有意侵入的——它犧牲實時性能換取數據。

    • 內存和存儲開銷： 性能分析還可能增加內存使用（緩衝區）併產生大型輸出文件。如果應用程序對內存敏感，大型追蹤緩衝區可能會擾亂緩存使用或內存分配模式。例如，啟用詳細追蹤可能會為緩衝區分配數百MB，可能導致應用程序更多緩存未命中。大多數工具讓你配置緩衝區大小，在丟失事件與內存開銷之間權衡。

    • 併發性擾動： 侵入性插樁可能改變調度。如果性能分析導致函數花費2倍時間，那可能改變線程如何交錯或GPU流如何獲取工作。例如，CPU上的大量插樁可能導致向GPU提供工作變慢，使GPU看起來利用不足，而實際上是性能分析器的開銷導致的。好的性能分析器嘗試量化或限制其開銷，以避免誤導用戶。有些提供"開銷補償"，或至少測量在性能分析代碼本身中花費的時間（TAU有時包括"性能分析器開銷"指標）。

    • 準確性與侵入性： 你想要的準確性/細節越多，通常產生的開銷越大。例如，記錄每個內存分配（如GPUprobe所做）可能減慢頻繁分配的應用程序，但GPUprobe發現在典型CUDA代碼中，相對開銷很小，因為這些調用不是極其頻繁且已經需要時間。如果有人運行每秒調用cudaMalloc數千次的微基準測試，GPUprobe的開銷可能變得更明顯（由於每次調用的上下文切換）。類似地，採樣有可調頻率：如果你在每個CPU核心上以10 kHz採樣，可能開始看到幾個百分點或更多的開銷，更令人不安的是，你可能稍微干擾CPU渦輪頻率或功耗。通常，選擇一個安全範圍作為默認值（如1 kHz）。

    • 並行可擴展性的開銷： 在分佈式運行（帶GPU的MPI）中，還需要考慮性能分析工具可能增加通信或I/O開銷。例如，如果每個等級嘗試寫入大型追蹤文件，I/O負載可能減慢速度。一些工具合併數據以避免太多輸出（Score-P合併追蹤等），但這可能在程序結束時造成同步開銷。如果不小心，開銷可能隨規模成倍增加，這就是為什麼在大規模HPC中通常首選採樣（每個進程固定開銷）。

    工具比較：

    • Nsight Systems: 設計用於低開銷系統性能分析，默認設置下通常<5%開銷（如果增加CPU採樣頻率或追蹤極多事件則更高）。它通常可以在生產中短時間運行。
    • Nsight Compute: 對目標內核有非常高的開銷（可能是數量級），不適合生產運行——它是開發者的診斷工具。
    • HPCToolkit: 採樣的開銷非常低（適合長時間HPC運行）。如果使用GPU PC採樣，GPU上的開銷可能中等（根據採樣率，該內核可能減速2倍）。但HPCToolkit默認只追蹤內核，幾乎不增加開銷。
    • Omnitrace: 中等開銷——潛在的許多函數動態插樁和採樣結合。它針對大型應用優化，但仍在做很多事。對於中等插樁，他們可能實現低幾十個百分點的開銷，但用戶應該選擇更窄的焦點以保持開銷可控。
    • GPUprobe: 對於它所做的事情，開銷非常低（<4%），因為它只鉤入幾個慢調用。它明確宣傳為輕量級。
    • DCGM: 極低開銷。它在後臺運行並只輪詢指標（這在GPU上通常可忽略——讀取計數器寄存器不是免費的，但微小，而且DCGM針對最小影響優化）。除非你設置極高的採樣頻率，否則它不會對GPU或CPU造成太大困擾。它適合始終開啟的監控。
    • TAU: 差異很大。如果只使用採樣或粗粒度插樁（MPI調用、高級循環），開銷很低。如果使用自動源代碼插樁以細粒度，開銷可能很高（可能是2倍或更多運行時間）。TAU提供許多選項來調整這一點，如從插樁中過濾出小函數。

    權衡總結： 對於日常性能工程，通常從低開銷廣泛工具（如Nsight Systems或HPCToolkit採樣）開始找主要問題，然後使用更高開銷的針對性工具（如Nsight Compute或在TAU中添加更多插樁）深入特定內核或代碼區域。新工具的實現者必須決定在這個光譜上的位置——新的始終開啟監控工具應該是低開銷的（可能基於採樣，如流式GPU性能計數器），而新的深度分析工具可以是侵入性的但謹慎使用。用戶通常需要意識到開銷，不要將性能分析器導致的減速與真實行為混淆（這就是為什麼使用多個工具交叉檢查或以不同採樣率運行是良好實踐）。

    安全和沙盒考慮

    性能分析工具通常需要低級訪問，這在共享系統或雲中引發安全和隔離問題：

    • 權限要求： 如前所述，在GPU上訪問硬件計數器通常默認限制為管理員（NVIDIA驅動程序默認NVreg_RestrictProfilingToAdminUsers=1防止非root用戶使用CUPTI指標或Nsight）。許多工具（Nsight、HPCToolkit）如果不禁用該限制或以root運行，將無法捕獲某些指標。原因是性能計數器可能被用作旁路通道（例如，計時另一個進程的GPU使用情況）。DCGM同樣可能需要提升權限進行某些操作，但其開源核心在適當配置下可以在用戶空間運行。
    • 容器化： 在容器（Docker/Kubernetes）內運行性能分析器很棘手。按設計，容器限制了對性能監控的訪問。例如，perf_event_paranoid sysctl在整個系統範圍內適用——在容器內部，如果主機設置不夠寬鬆，可能不允許性能分析。像Nsight這樣的工具如果獲得正確的權限可以在容器中運行（NVIDIA容器工具包可以傳遞GPU性能分析能力）。Kubernetes中有一個官方的DCGM容器用於監控GPU，它以特權方式運行以收集數據，然後通過網絡端點以安全方式向非特權消費者提供指標。如果在沒有權限的集群上嘗試在容器中運行HPCToolkit或TAU，它們可能無法附加到GPU事件。一些雲提供商出於安全考慮明確禁用其GPU上的性能分析。
    • 多租戶GPU： 如果兩個用戶共享一個GPU（通過MPS或虛擬化），性能分析可能失敗或潛在地暴露另一個用戶的活動。通常，供應商驅動程序通過僅限管理員的限制防止這種情況。AMD的ROCm可能允許多個用戶進程，但rocm性能分析可能只能看到你自己的隊列（儘管通常仍然需要root訪問性能計數器）。在多租戶場景中，運營商通常會允許監控（如DCGM聚合統計信息），但不允許任意用戶進行詳細追蹤。這是新性能分析工具必須考慮的事項——你可能必須與權限模型集成。例如，站點可能以特權服務運行性能分析器，用戶可以請求數據，而不是將二進制文件提供給用戶運行。
    • 插樁方法的安全性： eBPF和ptrace等技術（一些工具用於附加到進程）受Linux功能限制。默認情況下，一個進程不能ptrace另一個不同用戶的進程，非特權BPF可能受限（最近的內核允許一些帶限制的非特權BPF，但uprobes可能需要CAP_SYS_ADMIN，取決於配置）。因此，GPUprobe可能需要root或至少BPF功能才能將uprobes附加到另一個進程的libcudart。這限制了在生產中使用這樣的工具，除非安排了適當的權限。
    • 數據淨化： 性能分析數據可能無意中捕獲敏感信息（例如，地址、暗示數據大小的分配大小，甚至可能是專有算法的內核名稱）。因此，共享性能分析結果必須謹慎。一些工具在需要時匿名化某些數據（例如，可以過濾掉內核名稱或內存地址）。
    • DPU和隔離環境： 在DPU（如Nvidia BlueField，它有Arm CPU並運行自己的操作系統）中，你可以像在任何Linux服務器上一樣對DPU進行性能分析（因為BlueField運行Ubuntu）。但如果DPU在主機卸載任務到它的模式下運行，分析兩者之間的交互很複雜。可能需要分別分析主機和DPU，然後關聯。出於安全考慮，DPU通常隔離主機視圖——主機可能無法輕易地在沒有權限的情況下窺探DPU的進程。因此，分析DPU可能需要登錄到DPU的操作系統。這是一個新興領域；像DCGM這樣的工具目前不涵蓋DPU（DCGM是GPU特定的）。未來的"DPU分析器"可能需要考慮網絡安全（確保追蹤網絡數據包不會暴露數據內容）和多租戶（DPU可能為多個VM提供服務）。
    • 副作用： 一些插樁（如寫入/proc或加載內核模塊）在加固環境中可能被禁止。例如，要分析GPU，可能需要加載內核模塊（Linux nvidia 驅動程序有一些性能分析鉤子）。在HPC中心，管理員通常預先安裝並啟用需要的配置。在雲中，可能需要容器權限或特殊編排。

    簡而言之，在沙盒環境中進行性能分析通常需要管理員有意啟用。內部可觀察性平臺可能使用特權代理（如DCGM導出器）收集指標，並以受控方式向用戶暴露，而不是讓用戶在共享硬件上運行任意性能分析器。許多供應商正致力於使容器中的性能分析更易訪問（隨著NVIDIA Docker集成，NVIDIA對NVTX和某些CUPTI功能在容器中的支持有所改善）。

    對於構建新工具的人來說，明智的做法是瞭解這些限制，並可能設計工具使其能夠：

    • 在沒有特殊權限的情況下以減少功能模式運行（例如，只使用用戶空間計時，而非硬件計數器），或者
    • 部署為多個用戶可以安全使用的特權服務（可能通過經過身份驗證的API）。

    限制、注意事項和未來方向

    儘管功能強大，當前的GPU/DPU性能分析工具仍有限制。瞭解這些有助於識別未來工作的領域：

    • 一個工具中有限的供應商支持： 沒有單一工具能很好地覆蓋所有加速器。Nsight僅限NVIDIA；Omnitrace目前僅限AMD；Intel的工具僅限Intel。像HPCToolkit和TAU這樣的工具嘗試多平臺，但即使它們也需要每個供應商不同的後端，可能不會暴露每個供應商特定的指標。真正統一的性能分析標準仍然缺乏。OneAPI朝著CPU/GPU方向邁出了一步（通過Level Zero和插樁接口），但採用仍在進行中。未來的工作可以開發通用追蹤格式或API，使一個工具（或其插件）能夠無縫處理來自多個供應商的GPU。

    • 深度與開銷權衡： 如前所述，捕獲所有內容（長時間運行的完整追蹤）可能不可行。因此，工具要麼限制持續時間、頻率，要麼限制詳細程度。用戶需要注意，例如，Nsight Systems在緩衝區溢出時可能會丟棄事件，或者HPCToolkit可能不會記錄每個微小的內核（如果它們發生得太頻繁，通常會過濾掉非常短的內核以避免數據淹沒）。這意味著性能分析可能不是100%準確。需要注意的是，啟用性能分析可能會改變性能；例如，分析行為可能會使一些GPU操作序列化或改變時間，因此用戶必須將結果視為近似值。未來的性能分析器可能利用更多硬件支持來減少開銷（例如，硬件追蹤緩衝區，如CPU中的Intel PT；也許有一天GPU會有一個性能分析器可以收穫的硬件追蹤）。

    • DPU和異構工作負載性能分析： 分析DPU（數據處理單元）和緊密集成的系統（CPU和GPU共享內存的APU）是一個不斷發展的領域。對於DPU，由於它們結合了網絡、存儲和計算卸載，性能分析器需要捕獲網絡事件（數據包或協議處理）以及DPU的Arm核心上的CPU事件。今天，可能在DPU上使用標準Linux工具（如用於CPU的perf和可能通過ethtool的專用NIC計數器）。目前還沒有廣泛使用的專用DPU性能分析器，可以顯示，例如，"NIC中的這個流導致了DPU上的這個CPU處理"。未來的工作可以整合NIC遙測與CPU性能分析——例如，使用類似DPDK或DOCA庫在DPU上檢測數據包處理。

    • 對於APU（一個芯片上的CPU+GPU，共享內存），一個限制是許多性能分析工具仍然分別對待CPU和GPU。但APU可以啟用新型性能分析：由於它們共享內存，可以系統範圍地追蹤內存訪問。AMD的HSA旨在統一CPU/GPU內存空間，實際上，HSA的工具可以測量CPU對緩衝區的訪問和GPU訪問是否干擾等。我們還沒有看到主流工具顯示APU上CPU+GPU的組合緩存配置。未來研究可能允許追蹤APU中CPU和GPU之間的緩存一致性事件或內存流量，以查看爭用（例如，如果CPU和GPU爭奪內存帶寬，如何在性能分析中檢測？今天可能會看到CPU和GPU都顯示高內存使用率，但手動關聯它們）。

    • 另一個APU特定的挑戰是時間線對齊——在APU上，CPU和GPU時鐘可能更緊密耦合，甚至可能是相同的振盪器。這可能簡化相關性（不考慮PCIe延遲），但工具尚未利用任何特殊的APU功能。

    • 可擴展性： 隨著HPC邁向百億億次計算，同時分析數百或數千個GPU變得困難。HPCToolkit和TAU通過專注於採樣和分析（減少數據）而非巨大追蹤來解決這個問題。但即使每秒從100,000個節點收集一個樣本也是大量數據。未來方向包括在線分析（性能分析器即時分析和丟棄數據，只保留摘要或異常）和流式方法，只將有趣的事件發送到中央收集器。也許AI技術將應用於性能數據，智能決定記錄什麼。

    • 自動化和洞察生成： 目前，性能分析器呈現數據，由用戶推斷洞察（工具提供一些提示）。Nsight Compute有一個規則引擎來提示常見問題（"內存受限，嘗試增加併發性"等），但大多數工具不會自動確定根本原因。未來方向是更多自動性能診斷。例如，關聯模式："每當GPU空閒時，CPU線程X在互斥鎖中——可能是同步瓶頸。"一些研究工具或原型功能致力於這種專家系統。TAU與調優框架集成，可能可以自動對可疑熱點應用插樁。我們可能會看到更多性能異常檢測內置於性能分析器中（特別是對於始終開啟的監控，標記某次迭代比平常慢並給出可能原因）。

    • 能源和效率指標： 隨著加速器的增多，功率和能源性能分析變得重要。DCGM提供功率使用情況，但很少有工具將其與性能集成。許多性能分析器的一個限制是它們不容易將能源使用歸因到每個內核。未來，工具可以使用功率遙測來識別能源浪費的階段（GPU功率高但利用率低）。AMD和Intel通過RAPL或ROCm-smi支持一些功率指標；將這些集成到性能分析中正在進行。

    • 新型加速器： 除了DPU之外，還有TPU（谷歌的）、FPGA、定製ASIC。每種類型往往有自己的工具（谷歌TPU有集成在TensorBoard中的性能分析器）。社區面臨的挑戰是通過標準接口將性能分析推廣到任何加速器。朝這個方向發展的一個項目是開源Kokkos Tools，用於節點級性能分析，它抽象了設備。它允許通過通用API分析任何後端（CUDA、HIP等）。像HPCToolkit和TAU這樣的工具參與這些計劃，為新設備做好準備（如果加速器供應商提供類似OMPT或CUPTI的API，這些工具可以接入）。

    • 需要逆向工程： 開源工具經常需要追趕未記錄的功能。例如，在NVIDIA提供官方支持之前，HPCToolkit開發者必須弄清楚如何通過解析CUBIN中的ELF符號將GPU PC映射到源代碼，以及如何通過CUPTI的不斷發展的API收集GPU指標。這意味著當新硬件到來時，開源工具落後於供應商工具（供應商可能不會立即更新CUPTI等）。未來理想的情況是供應商開放更多驅動程序的插樁鉤子或標準化它們。同時，可以預期，對於前沿功能（如新GPU內存類型或新DPU卸載引擎），早期性能分析可能涉及創造性黑客技術或有限信息，直到官方支持趕上。

    總之，這一領域的未來工作可能會專注於統一和簡化異構性能分析的工具鏈，進一步減少開銷（可能通過硬件支持），將性能分析與監控集成（在生產中持續捕獲問題），以及更智能的分析來幫助開發者更快地找出問題。景觀正在向開放標準（如用於追蹤的Perfetto，也許有一天會出現類似PAPI的GPU標準）移動，這將使構建插入的自定義性能分析器更加容易。當前工具實現的洞察——它們的成功和痛點——將指導這些發展。隨著硬件繼續發展（芯片GPU、統一內存層次結構等），性能分析工具需要適應，但基本技術（插樁與採樣、硬件計數器使用、多流關聯）將仍然是任何性能分析工具包的基石。

    如何在 Linux 顯微鏡（LMP）項目中開啟 eBPF 之旅？

    eBPF 為 Linux 內核提供了可擴展性，使開發人員能夠對 Linux 內核進行編程，以便根據他們的業務需求快速構建智能的或豐富的功能。

    我們的 LMP(Linux Microscope) 項目 是為了充分挖掘 ebpf 的可能性而建立的，項目以構建 eBPF 學習社區、成為 eBPF 工具集散地、孵化 eBPF 想法和項目為目標，正在大力建設中。之前我們在 LMP 其中的 eBPF Supermarket 中包含了大量由個人開發者編寫的 eBPF 工具，覆蓋了網絡、性能分析、安全等多種功能，我們正在嘗試把其中的一些程序遷移到 eBPF Hub，一些規範化的 eBPF 程序庫，可以隨時下載運行，或嵌入大型應用程序中作為插件使用。

    我們嘗試在 eBPF Hub 中，基於 eunomia-bpf 開發框架創建符合 OCI 標準的 Wasm 和 eBPF 程序，並利用 ORAS 簡化擴展 LMP 的 eBPF 分發、加載、運行能力。

    快速使用

    如果您想快速開始 eBPF，可以使用我們開發的輕量級框架之上的命令行程序 lmp-cli。當使用腳本安裝好我們的框架之後，您只需要一條命令，無需任何編譯，即可體會到 eBPF 的強大之處：

    $ lmp run sigsnoop
download with curl: https://linuxkerneltravel.github.io/lmp/sigsnoop/package.json
running and waiting for the eBPF events from perf event...
time pid tpid sig ret comm
00:21:41 109955 112863 28 0 gnome-terminal-
00:21:41 109955 112862 28 0 gnome-terminal-
...

    如果您使用過 bcc 等 eBPF 開發工具，您一定會驚喜於 LMP 的便捷性。LMP 中包含了各種各樣的 eBPF 程序，這種便捷的運行，離不開我們基於的底層框架 eunomia-bpf，它完全實現了“一次編譯，處處運行”的 eBPF 跨平臺目標。在 eunomia-bpf 框架下，LMP 開發的 eBPF 應用不僅可以適配任意架構和不同內核版本，而且還具有輕量級、良好的隔離性等優點，可以作為插件到嵌入大型應用之中。

    eunomia-bpf：結合 eBPF 和 Wasm 的輕量級開發框架

    作為一個 eBPF 程序的輕量級開發加載框架，eunomia-bpf 基於 Wasm 運行時和 BTF 技術，包含了一個用戶態動態加載框架/運行時庫，以及一個簡單的編譯 Wasm 和 eBPF 字節碼的工具鏈容器。

    Wasm 是為了一個可移植的目標而設計的，可作為 C/C+/RUST 等高級語言的編譯目標，使客戶端和服務器應用程序能夠在 Web 上部署。目前已經發展成為一個輕量級、高性能、跨平臺和多語種的軟件沙盒環境，被運用於雲原生軟件組件。 eunomia-bpf 將 eBPF 用戶態的所有控制和數據處理邏輯全部移到 Wasm 虛擬機中，通過 Wasm module 打包和分發 eBPF 字節碼，同時在 Wasm 虛擬機內部控制整個 eBPF 程序的加載和執行，將二者的優勢結合了起來。

    在 Wasm 模塊中編寫 eBPF 代碼和通常熟悉的使用 libbpf 框架或 Coolbpf 開發 eBPF 程序的方式是基本一樣的，Wasm 的複雜性會被隱藏在 eunomia-bpf 的編譯工具鏈和運行時庫中，開發者可以專注於 eBPF 程序的開發和調試，不需要了解 Wasm 的背景知識，也不需要擔心 Wasm 的編譯環境配置。

    大致來說，eunomia-bpf 在 Wasm 運行時和用戶態的 libbpf 中間多加了一層抽象層，使得一次編譯、到處運行的 eBPF 代碼可以從 JSON 對象中動態加載。JSON 對象會在編譯時被包含在 Wasm 模塊中，因此在運行時，我們可以通過解析 JSON 對象來獲取 eBPF 程序的信息，然後動態加載 eBPF 程序。通過 Wasm module 打包和分發 eBPF 字節碼，同時在 Wasm 虛擬機內部控制整個 eBPF 程序的加載和執行，eunomia-bpf 就可以將二者的優勢結合起來，讓任意 eBPF 程序能有如下特性：

    • 可移植：讓 eBPF 工具和應用不需要進行重新編譯即可以跨平臺分發，省去了複雜的交叉編譯流程；
    • 隔離性：讓 eBPF 程序的加載和執行、以及用戶態的數據處理流程更加安全可靠。
    • 包管理：完成 eBPF 程序或工具的分發、管理、加載等工作。
    • 敏捷性：使每個人都可以使用官方和未經修改的應用程序來加載自定義擴展，任何 eBPF 程序的錯誤修復和/或更新都可以在運行時推送和/或測試，而不需要更新和/或重新部署一個新的二進制。
    • 輕量級：與 Linux 容器應用相比，Wasm 微服務冷啟動的時間是 1%，可以實現 eBPF as a service，讓 eBPF 程序的加載和執行變得更加輕量級、快速、簡便易行。

    我們已經測試了在 x86、ARM 等不同架構不同內核版本的 Linux 系統上，eunomia-bpf 框架都可以使用同一個預編譯 eBPF 程序二進制，從雲端一行命令獲取到本地之後運行。之後 eunomia-bpf 還會添加 RISC-V 等更多架構的支持。

    使用 lmp-cli 構建一個 eBPF 項目

    如果您是一個 eBPF 工具的使用者，您可以無需任何編譯流程，也不需要了解任何 eBPF 和 Wasm 的相關知識，使用 lmp run <name> 就可以直接運行 LMP 倉庫的小程序，其中會調用lmp pull <name>命令從雲端從庫中下載對應的小程序。

    如果您是一個 eBPF 程序的開發者，讓我們開始創建、編譯並運行一個簡單的程序。在這裡，我們使用基簡單命令行工具 lmp-cli，概述如何從四個步驟開始構建。

    1. 準備你的環境

    eBPF 本身是一種 Linux 內核技術，因此任何實際的 BPF 程序都必須在 Linux 內核中運行。我建議您從內核 5.4 或更新的版本開始。從 SSH 終端，檢查內核版本，並確認您已經啟用了 CONFIG_DEBUG_INFO_BTF：

    uname -r
cat /boot/config-$(uname -r) | grep CONFIG_DEBUG_INFO_BTF

    你會看到類似這樣的輸出：

    $ uname -r
5.15.0-48-generic

$ cat /boot/config-$(uname -r) | grep CONFIG_DEBUG_INFO_BTF
CONFIG_DEBUG_INFO_BTF=y
CONFIG_DEBUG_INFO_BTF_MODULES=y

    安裝命令行工具 lmp-cli：

    curl https://github.com/GorilaMond/lmp_cli/releases/download/lmp/install.sh | sh

    2. 創建項目的內核部分

    使用lmp init創建一個項目模板，來初始化你的內核程序，快速地投入到代碼的編寫中：

    lmp init hello

    成功創建項目後，您將看到如下類似的輸出：

    $ lmp init hello
Cloning into 'ebpm-template'...

    它實際上創建了一個項目名對應的文件夾，裡面有這些文件：

    $ cd hello/
$ ll
...
-rw-rw-r--  1 a a 2910 10月 17 23:18 bootstrap.bpf.c
-rw-rw-r--  1 a a  392 10月 17 23:18 bootstrap.h
-rw-rw-r--  1 a a  221 10月 17 23:18 config.json
drwxrwxr-x  8 a a 4096 10月 17 23:18 .git/
drwxrwxr-x  3 a a 4096 10月 17 23:18 .github/
-rw-rw-r--  1 a a   21 10月 17 23:18 .gitignore

    3. 運行內核程序

    可以使用lmp run package.json運行內核程序，沒有用戶端程序對數據的處理的情況下，該框架下內核程序將會輸出所有被 output 的數據：

    $ sudo lmp run ./package.json

    23:31:31 111788 109955 0 0 bash /bin/bash 0

    另一個例子：使用 eBPF 打印進程內存使用狀況

    可以將 bootstrap.bpf.c 重命名為 procstat.bpf.c，將 bootstrap.h 重命名為 procstat.h，然後編譯運行。對應的源代碼如下：

    procstat.bpf.c

    #include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>
#include <bpf/bpf_core_read.h>
#include "procstat.h"

char LICENSE[] SEC("license") = "Dual BSD/GPL";

struct {
 __uint(type, BPF_MAP_TYPE_RINGBUF);
 __uint(max_entries, 256 * 1024);
} rb SEC(".maps");


SEC("kprobe/finish_task_switch")
int BPF_KPROBE(finish_task_switch, struct task_struct *prev)
{
 struct event *e;
 struct mm_rss_stat rss = {};
 struct mm_struct *mms;
 long long *t;

 e = bpf_ringbuf_reserve(&rb, sizeof(*e), 0);
 if (!e)
  return 0;

 e->pid = BPF_CORE_READ(prev, pid);
 e->vsize = BPF_CORE_READ(prev, mm, total_vm);
 e->Vdata = BPF_CORE_READ(prev, mm, data_vm);
 e->Vstk = BPF_CORE_READ(prev, mm, stack_vm);
 e->nvcsw = BPF_CORE_READ(prev, nvcsw);
 e->nivcsw = BPF_CORE_READ(prev, nivcsw);

 rss = BPF_CORE_READ(prev, mm, rss_stat);
 t = (long long *)(rss.count);
 e->rssfile = *t;
 e->rssanon = *(t + 1);
 e->vswap = *(t + 2);
 e->rssshmem = *(t + 3);
 e->size = *t + *(t + 1) + *(t + 3);

 bpf_ringbuf_submit(e, 0);
 return 0;
}

    proc.h

    #ifndef __BOOTSTRAP_H
#define __BOOTSTRAP_H

#define TASK_COMM_LEN 16
#define MAX_FILENAME_LEN 127

struct event {
/*進程內存狀態報告*/
    pid_t pid;
    long nvcsw;
    long nivcsw;
    long vsize;              //虛擬內存
    long size;               //物理內存
    long long rssanon;       //匿名頁面
    long long rssfile;       //文件頁面
    long long rssshmem;      //共享頁面
    long long vswap;         //交換頁面
    long long Hpages;        //hugetlbPages
    long Vdata;              //Private data segments
    long Vstk;               //User stack
    long long VPTE;
};
#endif /* __BOOTSTRAP_H */

    具體的上報事件信息在 event 結構體中定義：

    參數 含義
    vsize 進程使用的虛擬內存
    size 進程使用的最大物理內存
    rssanon 進程使用的匿名頁面
    rssfile 進程使用的文件映射頁面
    rssshmem 進程使用的共享內存頁面
    vswap 進程使用的交換分區大小
    vdata 進程使用的私有數據段大小
    vpte 進程頁表大小
    vstk 進程用戶棧大小

    掛載點與掛載原因分析：

    • 首先，獲取進程級別內存使用信息需要獲取到進程的 task_struct 結構體，其中在 mm_struct 成員中存在一個保存進程當前內存使用狀態的數組結構，因此有關進程的大部分內存使用信息都可以通過這個數組獲得。
    • 其次，需要注意函數的插入點，插入點的選取關係到數據準確性是否得到保證，而在進程的內存申請，釋放，規整等代碼路徑上都存在頁面狀態改變，但是數量信息還沒有更新的相關結構中的情況，如果插入點這兩者中間，數據就會和實際情況存在差異，所有在確保可以獲取到進程 PCB 的前提下，選擇在進程調度代碼路徑上考慮。而 finish_task_switch 函數是新一個進程第一個執行的函數，做的事卻是給上一個被調度出去的進程做收尾工作，所以這個函數的參數是上一個進程的 PCB，從這塊獲得上一個進程的內存信息就可以確保在它沒有再次被調度上 CPU 執行的這段時間內的內存數據穩定性。
    • 因此最後選擇將程序掛載到 finish_task_switch 函數上。數據來源有兩部分，一個是 mm_struct 結構本身存在的狀態信息，另一個是在 mm_rss_stat 結構中。

    相關背景

    LMP 項目的成立初衷是：

    • 面向 eBPF 初學者和愛好者，提供 eBPF 學習資料、程序/項目案例，構建 eBPF 學習社區
    • 成為 eBPF 工具集散地，我們相信每一位 eBPF 初學者和愛好者都有無限的創造力
    • 孵化 eBPF 想法、相關工具、項目

    LMP 目前分為四個子項目：

    • eBPF_Supermarket 中包含了大量由個人開發者編寫的 eBPF 工具，覆蓋了網絡、性能分析、安全等多種功能；
    • eBPF_Hub 是規範化的 eBPF 程序庫，可以隨時下載運行；
    • eBPF_Visualization 是為 eBPF 程序管理而開發的 web 管理系統，聚焦 eBPF 數據可視化和內核可視化；
    • eBPF_Documentation 為社區收集、梳理和原創的 eBPF 相關資料和文檔。

    當前 LMP 項目也存在一些問題，例如對於 eBPF 工具的開發者，存在非常多而且複雜的用戶態可視化、展示方案，有許多套系統提供可視化的實現並且有多種語言混合，缺乏展示標準、也難以進行可視化的整合等。因此，我們希望嘗試藉助 eunomia-bpf 提供的符合 OCI 標準的 Wasm 和 eBPF 程序，提供標準化、高可擴展性的基於 eBPF 的可視化、數據展示、分析平臺，利用 ORAS 簡化擴展 eBPF 的分發、加載、運行能力，為 eBPF 工具的開發者和使用者提供更加簡單、高效的體驗。

    WebAssembly

    WebAssembly 是一種新的編碼方式，可以在現代的網絡瀏覽器中運行 － 它是一種低級的類彙編語言，具有緊湊的二進制格式，可以接近原生的性能運行，併為諸如 c\c++ 等語言提供一個編譯目標，以便它們可以在 Web 上運行。它也被設計為可以與 JavaScript 共存，允許兩者一起工作。而且，更棒的是，這是通過 W3C WebAssembly Community Group 開發的一項網絡標準，並得到了來自各大主要瀏覽器廠商的積極參與。

    儘管 WebAssembly 是為運行在 Web 上設計的，它也可以在其它的環境中良好地運行。包括從用作測試的最小化 shell ，到完全的應用環境 —— 例如：在數據中心的服務器、物聯網（IoT）設備或者是移動/桌面應用程序。甚至，運行嵌入在較大程序裡的 WebAssembly 也是可行的。通常，通過維持不需要 Web API 的非 Web 路徑，WebAssembly 能夠在許多平臺上用作便攜式的二進制格式，為移植性、工具和語言無關性帶來巨大的好處。（因為它支持 c\c++ 級語義）

    OCI(Open Container Initiative)

    開放容器協議(OCI)是一個輕量級，開放的治理結構，為容器技術定義了規範和標準。在 Linux 基金會的支持下成立，由各大軟件企業構成，致力於圍繞容器格式和運行時創建開放的行業標準。其中包括了使用 Container Registries 進行工作的 API，正式名稱為 OCI 分發規範(又名“distribution-spec”)。這個發佈規範是基於 Docker 公司最初發布的開源註冊服務器編寫的，它存在於 GitHub 的distribution/distribution（現在是CNCF項目）上。

    OCI 目前提出的規範有如下這些：

    名稱 版本
    Runtime Specification v1.0.2
    Image Format v1.0.2
    Distribution Specification v1.0.1

    其中 runtime 和 image 的規範都已經正式發佈，而 distribution 的還在工作之中。runtime 規範中介紹瞭如何運行解壓縮到磁盤上的 Filesystem Bundle。在 OCI 標準下，運行一個容器的過程就是下載一個 OCI 的鏡像，將其解壓到某個 Filesystem Bundle 中，然後某個 OCI Runtime 就會運行這個 Bundle。

    伴隨著 image spec 與 distribution spec 的演化，人們開始逐步認識到除了 Container Images 之外，Registries 還能夠用來分發 Kubernetes Deployment Files, Helm Charts, docker-compose, CNAB 等產物。它們可以共用同一套 API，同一套存儲，將 Registries 作為一個雲存儲系統。這就為帶來了 OCI Artifacts 的概念，用戶能夠把所有的產物都存儲在 OCI 兼容的 Registiry 當中並進行分發。為此，Microsoft 將 oras 作為一個 client 端實現捐贈給了社區，包括 Harbor 在內的多個項目都在積極的參與。

    ORAS(OCI Registry As Storage)

    Registries 正在逐漸演變為通用的組件存儲庫。為了實現這一目標，ORAS 項目提供了一種將 OCI Artifacts 從 OCI Registries 提交和拉取的方法。正在尋求通用 Registries 客戶端的用戶可以從ORAS CLI中得到幫助，而開發人員可以在ORAS 客戶端的開發庫之上構建自己的客戶端。

    ORAS 的工作原理與您可能已經熟悉的工具(如 docker)類似。它允許您向 OCI Registries 推送(上傳)和提取(下載)內容，並處理登錄(身份驗證)和令牌流(授權)。ORAS 的不同之處在於將焦點從容器映像轉移到其他類型的組件上。

    因此，鼓勵新的 OCI Artifacts 的作者定義他們自己的組件媒體類型，以使得他們的用戶知道如何對其進行操作。

    如果您希望立即開始發佈 OCI Artifacts，請查看ORAS CLI。希望提供給自己用戶體驗的開發人員應該使用一個 ORAS 客戶端開發庫。

    未來的發展方向

    未來 LMP 會專注於更多的基於 eBPF 的應用工具和實踐的開發：

    1. 進一步完善 ORAS 和 OCI 鏡像相關的支持；
    2. 重構並遷移現有的 eBPF 工具，提供完整的、開箱即用的分析工具組件，例如性能工程等方面；
    3. 探索和孵化更多的 eBPF 想法、相關工具、項目；

    我們所基於的 eunomia-bpf 項目也會繼續完善，專注於提供一個底層的 eBPF 開發平臺和運行時基礎設施，力求帶來更好的開發和移植體驗：

    1. 測試更多平臺和內核版本的支持，目前已經在 ARM64 和 x86_64 上成功移植並運行，接下來會對低內核版本、Android、RISC-V 等平臺，以及嵌入式、邊緣計算相關的設備進行更進一步的測試；也許在未來，我們還可以提供 Windows 上的 eBPF 程序支持和類似的開發體驗；
    2. 提供標準化、穩定的 JSON 和 Wasm 接口協議規範以及 OCI 鏡像規範，不和任何的供應商或雲服務綁定。如果不使用 eunomia-bpf 相關的底層運行時，或使用自定義的 Wasm 運行時，也可以通過標準化的接口來使用 LMP 中已經有的大量 eBPF 程序生態。
    3. 提供更友好的用戶態開發接口，以及更多的用戶態開發語言 SDK，例如 Go、Rust、Python 等；
    4. 進行更多關於 Wasm 和 eBPF 結合的探索；

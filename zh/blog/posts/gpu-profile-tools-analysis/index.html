    加速器工具箱：GPU和其他協處理器的性能分析和追蹤詳解

    現代計算越來越依賴專用加速器——尤其是GPU、DPU和APU——來處理各種工作負載。圖形處理單元(GPU)是一種大規模並行處理器，最初用於圖形處理，現在在通用計算(HPC)和AI中必不可少。數據處理單元(DPU)是一種較新類型的可編程處理器，結合了CPU核心和高性能網絡/存儲引擎。DPU從CPU卸載網絡、安全和存儲任務，被認為是繼CPU和GPU之後計算的"第三支柱"。同時，加速處理單元(APU)在一個芯片上集成了CPU和GPU組件——這一方法由AMD的Fusion架構首創——實現了統一內存和高吞吐量，適用於HPC和AI工作負載。這些加速器運行各種工作負載：GPU在並行數學（HPC模擬、深度學習訓練/推理、數據分析）和圖形渲染方面表現出色；DPU專注於數據中心任務（網絡數據包處理、加密、存儲卸載、虛擬化）；而APU針對需要緊密CPU-GPU耦合的異構工作負載（例如共享內存的AI或多媒體應用程序）。

    性能分析和追蹤工具對於優化這些加速器上的性能至關重要。這些工具收集低級硬件遙測數據（例如利用率、內存吞吐量、SM佔用率、緩存未命中等計數器）並可以執行指令或事件級追蹤（捕獲內核執行、內存複製、網絡數據包流等的時間線）。目標是識別通用代碼和特定領域流水線（如ML模型訓練、網絡功能處理或圖形渲染）中的瓶頸和低效率。然而，對高度並行、異構系統進行性能分析帶來了開銷、數據量和跨平臺兼容性的挑戰。本綜述按硬件類型和領域對當前追蹤/性能分析工具進行分類，比較開源和商業解決方案，並強調主要項目和最新研究。我們還討論專門的工具集（包括類似於Linux BCC的基於eBPF的方法）如何適應GPU/DPU/APU，典型工作負載和匹配工具鏈，以及這一領域的侷限和新興方向。

    GPU的性能分析和追蹤工具

    GPU性能分析經過多年圖形和GPGPU開發的成熟，形成了豐富的廠商工具和開源框架生態系統。廣義上，GPU性能分析器分為兩類：開發時性能分析器，提供細粒度洞察以優化（通常具有高開銷和GUI分析），以及輕量級監控器，適用於運行時或生產環境（低開銷，專注於高級指標）。

    • NVIDIA的性能分析套件： NVIDIA的GPU在HPC/AI中占主導地位，其工具被認為是行業標準。Nsight Systems提供系統範圍的時間線追蹤——捕獲CPU線程、CUDA內核啟動、內存複製等——以精確定位CPU-GPU邊界上的瓶頸。它使用CUDA性能分析工具接口(CUPTI)收集詳細的指標和事件。Nsight Systems對深入分析GPU加速應用程序極其強大，但它必須顯式啟動性能分析會話，並可能產生顯著開銷（在性能分析期間通常使程序速度降低2×–10×）。它適用於開發和調優，而非持續使用。另一方面，Nsight Compute專注於逐內核深入分析：它分析單個GPU內核，提供指令級統計（如指令混合、內存事務、warp佔用率、執行停滯）甚至可以將性能指標與源代碼行或PTX/SASS彙編關聯。NVIDIA還提供Visual Profiler（一個較舊的GUI，現在主要被Nsight取代）和通過nvprof/nsys進行命令行性能分析。對於圖形工作負載（DirectX、OpenGL、Vulkan），NVIDIA的Nsight Graphics捕獲幀渲染管線、著色器計時和GPU狀態以輔助遊戲開發者。所有這些NVIDIA工具都是免費但專有（閉源）的。它們針對NVIDIA硬件進行嚴格優化，並支持特定領域的分析模式（圖形vs計算vs AI）。

    • AMD的GPU性能分析工具： AMD提供開源和專有工具作為ROCm和GPUOpen生態系統的一部分。歷史上，CodeXL是AMD的用於CPU、GPU和APU的多合一性能分析器和調試器。CodeXL（現已停止）可以分析AMD APU/GPU上的OpenCL、HIP和HSA應用程序，收集內核執行時間和集成設備上的硬件計數器。近年來，AMD轉向基於ROCm的工具：rocProfiler和rocTracer庫（類似於NVIDIA的CUPTI）使HIP和OpenCL應用程序能夠進行性能分析和追蹤。2024年，AMD在ROCm 6.2中引入了新工具：Omniperf和Omnitrace。Omniperf是AMD Instinct GPU上機器學習和HPC工作負載的內核級性能分析器，通過CLI或GUI儀表板提供詳細的性能計數器分析。Omnitrace是一個多用途性能分析/追蹤工具，用於CPU和GPU，支持動態二進制插樁、調用棧採樣，甚至因果性能分析，以精確指出在異構CPU-GPU執行中哪些函數消耗時間。這些工具是開源的，或者是AMD開放ROCm棧的一部分。對於圖形和遊戲開發，AMD在GPUOpen下提供Radeon GPU Profiler (RGP)和Radeon Developer Panel。RGP為Radeon GPU上的Vulkan/DX12應用程序提供低級時間線和波前佔用數據，而Radeon Memory Visualizer幫助跟蹤內存使用情況。AMD的工具也可以在他們的APU上使用，受益於統一內存（例如，在APU上進行性能分析意味著可以追蹤GPU內核而不需要PCIe傳輸開銷）。總體而言，AMD的方法強調開放接口（例如，GPUPerfAPI庫讓開發者直接訪問GPU性能計數器）和與通用性能分析器的集成。

    • Intel和其他GPU工具： Intel的GPU（集成Iris Xe和數據中心GPU如Ponte Vecchio）可以通過Intel的oneAPI工具集進行性能分析。Intel VTune Profiler支持GPU卸載分析，提供內核時間線、EU（執行單元）佔用率和Intel GPU的內存帶寬。Intel還提供Graphics Performance Analyzers (GPA)用於在Intel硬件上進行遊戲/圖形性能分析。值得注意的是，Intel開源了一套名為Profiling Tools Interface (PTI) for GPU的工具，其中包括用於oneAPI Level Zero和OpenCL應用程序的輕量級追蹤工具。這些命令行工具（在GitHub上可用）可以在Intel GPU上追蹤GPU內核提交、內存操作等，反映了Intel推動開放性能分析生態系統的努力。除了三大供應商之外，還有特定領域的GPU性能分析器：例如，ARM的Mali GPU（用於移動設備）有ARM Mobile Studio，其中包括用於分析移動GPU工作負載的Streamline工具；Qualcomm Adreno GPU可以使用高通的Snapdragon Profiler進行分析。這些更專業化的工具強調，跨供應商的性能分析通常需要特定於每種架構的專有SDK或工具，標準化程度較低——如果需要支持多個GPU供應商，這是一個痛點。

    • HPC和跨平臺性能分析： 在供應商特定工具之外，HPC社區開發了強大的開源性能分析框架，這些框架可以跨CPU和加速器工作。HPCToolkit是一個突出的例子：它使用統計採樣以最小開銷（通常<5%）對CPU和GPU執行進行性能分析。HPCToolkit可以在NVIDIA、AMD和Intel GPU上追蹤GPU操作（內核、內存複製、同步），並且在NVIDIA上它甚至利用硬件PC採樣來測量指令級執行和停滯週期。該工具將GPU活動關聯回CPU調用棧，允許一個統一的分析，將GPU成本歸因於調用的CPU代碼上下文。這對異構應用程序非常寶貴，例如識別哪個CPU端函數啟動了一個慢速GPU內核。其他跨平臺工具包括TAU和Score-P/Extrae，它們可以對MPI+GPU程序進行插樁併產生集成的追蹤。例如，Extrae追蹤器（來自BSC）記錄CPU事件和CUDA運行時事件，使得在Paraver中可以同時可視化CPU時間線和GPU內核時間線。這些開源工具通常通過插件支持多種加速器（CUDA用CUPTI，AMD用ROCm工具等），提供廠商中立的分析。它們可能不總是公開供應商工具指標的全部深度，但它們在協調多節點、多加速器追蹤方面表現出色。學術界的努力如Paraver/Extrae、Vampir和Allinea MAP (Arm Forge)已經發展到能夠處理GPU加速的HPC代碼，表明了向異構系統統一性能分析的趨勢。

    • 圖形和遊戲性能分析： 在圖形領域，追蹤GPU工作負載通常涉及捕獲API調用和GPU命令流。開源項目如RenderDoc允許逐幀捕獲Vulkan/OpenGL/Direct3D調用，並提供GPU繪製調用計時的內省（有助於圖形調試/性能）。雖然RenderDoc更多是一個調試器，但它可以提供關於GPU是否受某些繪製調用或著色器限制的洞察。也存在特定平臺的工具：微軟的PIX（用於Windows/Xbox上的DirectX）為每個渲染通道提供詳細的GPU計時，甚至Linux也有GPUView等工具，可以為圖形工作負載追蹤內核級GPU調度事件。這些工具高度特定於領域（針對圖形管線而非通用計算）。它們通過專注於幀渲染延遲而非內核吞吐量來補充通用GPU性能分析器。

    低開銷和持續監控的GPU追蹤

    經典的GPU性能分析器（如上所述）在開發過程中非常有用，但它們的開銷和侵入性工作流程使其不適合在生產環境中進行持續監控（例如，你不能僅僅為了收集追蹤而讓一個實時AI推理服務器的速度降低5倍）。為了填補這一空白，最近的工具利用了受Linux eBPF啟發的低開銷追蹤技術。一個值得注意的方法是Meta在eBPF峰會上由Selim (2023)介紹的eBPF用於全隊規模的GPU性能分析。Meta的工具不是對GPU代碼進行插樁，而是通過eBPF附加到GPU驅動程序事件，使其能夠以可忽略的開銷在數千臺機器上持續收集GPU指標。

    這一領域的一個開源項目例子是GPUprobe，一個基於Linux eBPF的GPU可觀察性工具。GPUprobe使用uprobes（用戶級探針）在內核級別鉤入NVIDIA的CUDA運行時庫函數。通過這樣做，它可以實時監控像GPU內存分配（cudaMalloc/free）和內核啟動等事件——無需對目標應用程序代碼進行任何修改或插樁。開銷非常低（在基準測試中測量低於4%），因此可以在生產環境中持續運行。GPUprobe填補了重型性能分析器和粗粒度監控之間的中間地帶：它提供比NVIDIA的數據中心GPU管理器(DCGM)更豐富的、每個應用程序的洞察——例如跟蹤每個進程和內核啟動頻率的內存洩漏——但開銷遠低於Nsight的完整性能分析。正如GPUprobe作者所指出的，Nsight Systems就像一個"GPU特定調試器"，非常適合深入分析但不適合持續使用，而DCGM提供高級統計數據（利用率、溫度、健康狀況）但缺少特定於應用程序的詳細信息。像GPUprobe這樣的工具彌補了這一差距，將指標導出到標準可觀察性系統（例如Prometheus/Grafana）以集成到數據中心儀表板中。事實上，GPUprobe的設計允許以OpenMetrics格式抓取其指標（內存使用圖、內核啟動計數、帶寬使用），因此操作員可以在Grafana中與CPU、網絡和其他指標一起可視化GPU行為隨時間的變化。

    這種BCC/eBPF啟發的方法是GPU性能分析的一個新興趨勢。它旨在將強大的內核追蹤方法（由perf、bcc和eBPF等工具在CPU上開創）引入GPU領域。研究原型甚至探索了在GPU本身上運行eBPF程序（例如，一個學術項目"eGPU"通過PTX注入將BPF字節碼卸載到GPU上），儘管這樣的技術尚未成為主流。目前，更實用的用途是從CPU端鉤入GPU驅動程序或運行時事件。結果是對GPU操作的非侵入性窺視：例如，檢測GPU作業是否受啟動限制（許多小內核啟動）或容易內存洩漏，無需重新編譯應用程序。這對雲提供商或大規模AI部署特別有價值，持續性能分析可以捕獲長時間運行的GPU服務中的性能迴歸或資源洩漏。

    DPU（智能網卡）的性能分析和追蹤工具

    DPU（數據處理單元），通常以智能網卡的形式出現，結合了通用處理核心和專用數據包處理硬件。它們用於從主CPU卸載網絡（數據包交換、虛擬化）、存儲（NVMe-oF、加密）和安全任務。DPU的性能分析提出了一個獨特的挑戰：必須同時考慮板載CPU（通常是運行Linux的Arm SoC）和網絡數據面，後者可能涉及網卡上的FPGA邏輯或ASIC加速器。

    一般來說，DPU上的性能分析可以利用許多標準Linux工具用於嵌入式CPU部分。例如，NVIDIA的BlueField DPU運行Ubuntu，因此可以使用Linux perf、標準CPU性能分析器，甚至基於eBPF的監視器在DPU的Arm核心上對本地運行的軟件（例如，卸載的軟件交換機）進行性能分析。如果用戶應用程序或代理在DPU的操作系統上運行，它的性能分析方式與在任何Linux服務器上很相似——儘管要意識到有限的核心和獨特的任務（通常是數據包處理線程）。事實上，可以在BlueField上運行BCC工具來測量系統調用，或使用perf對DPU代碼中的緩存未命中進行採樣。這是DPU上的通用工作負載性能分析（類似於任何Linux主機，但資源受限）。

    然而，DPU的許多工作負載是特定領域的（網絡和存儲），由專用硬件塊處理。例如，DPU可能在硬件中加速Open vSwitch (OVS)數據路徑，或通過專用引擎執行RDMA和NVMe操作。這些方面的性能分析通常依賴於供應商提供的遙測和計數器。像NVIDIA（Mellanox）和Broadcom這樣的供應商提供工具來監控其智能網卡上的數據包吞吐量、延遲和卸載引擎統計數據。NVIDIA的DOCA SDK for BlueField包括用於加速功能（例如，加密、RDMA）的性能分析API和性能監視器。BlueField DPU通過標準接口（可能通過DPDK或/sys計數器）暴露每秒數據包數、丟包和隊列深度等指標。在DPDK（與智能網卡一起使用的常見用戶空間數據包I/O庫）的情況下，開發者可以使用Intel VTune或perf對CPU上的數據包處理管道進行性能分析，並使用DPDK的內置事件計數器測量NIC吞吐量。Intel的文檔甚至涵蓋了使用VTune分析其基礎設施處理單元(IPU)上的DPDK事件調度。

    商業智能網卡供應商提供自己的監控套件。例如，Napatech（一家智能網卡製造商）分發性能分析工具，報告端口吞吐量、數據包計數器（RMON統計數據），甚至主機應用程序交互指標。這些工具通常以命令行監視器或GUI儀表板的形式出現。Napatech的監控CLI（在其文檔中顯示）可以實時更新線路速率（例如，在100G NIC上約48 Gbps Rx/Tx）和各種數據包大小計數器。這類供應商工具通常是專有的（與NIC捆綁在一起），突顯了與GPU領域的相似之處：要獲得對DPU上硬件加速器的完全可見性，通常使用供應商的API或實用程序。另一個例子：Broadcom/Pensando DPU（現在是AMD的一部分）有一個SDK，可能包括其數據包處理器的遙測，儘管詳細信息通常隱藏在NDA之後。思科和Marvell同樣為其智能網卡提供可管理性接口（通常作為網絡操作系統或NIC固件的一部分），專注於吞吐量和延遲指標，而非指令級追蹤。

    話雖如此，開源努力正在為智能網卡性能分析而興起。用於對某些NIC進行編程的P4語言有調試工具，可以模擬或記錄數據包通過管道的流程（儘管不完全是傳統意義上的性能分析器）。學術研究已經產生了像Clara和Pipefuse這樣的工具，用於分析甚至預測智能網卡上的網絡功能性能。這些工具旨在回答"如果我將這個功能卸載到智能網卡，可以預期什麼吞吐量？"之類的問題，通過對NIC資源進行建模。雖然不是運行時性能分析器，但它們解決了DPU工作負載更廣泛的性能調優問題。另一個研究例子是LogNIC，它為智能網卡管道提供性能模型。這類工具主要是實驗性的，但指向未來的高級性能分析器用於網絡任務。

    總之，今天的DPU性能分析是CPU性能分析和專用網絡遙測的拼湊組合。一方面可能使用熟悉的工具對DPU上的軟件控制平面進行性能分析（以確保DPU的CPU不是瓶頸），同時使用NIC計數器或合成流量測試對數據平面吞吐量進行性能分析。協調這些通常是手動的。例如，要對卸載到DPU的Open vSwitch進行性能分析，你會測量DPU的CPU使用情況（控制任務、流設置）並收集NIC統計數據以瞭解數據包速率和延遲，可能通過生成測試流量並測量端到端延遲。網絡工作負載的標準性能分析器（例如如何在硬件上追蹤P4程序）仍處於起步階段。我們預計，隨著DPU變得更加普遍，廠商中立的性能分析標準可能會出現——可能是eBPF/XDP的擴展，以通過智能網卡進行追蹤，或NIC的開放遙測模式——但目前很多內容都是廠商特定的。

    APU（CPU-GPU集成平臺）的性能分析和追蹤工具

    加速處理單元（APU）將CPU和GPU集成在單個芯片上，共享內存和互連。AMD最新的Instinct MI300A是一個典型例子：一個數據中心APU，在一個封裝中結合了24個Zen4 CPU核心、128 GB的HBM內存和CDNA3 GPU。對APU進行性能分析需要理解片上CPU和GPU之間的交互，這既是一種優勢也是一種挑戰。一方面，統一內存意味著開發者不需要分析PCIe傳輸瓶頸——CPU和GPU可以訪問同一個HBM池，數據移動通過指針而非顯式複製。另一方面，APU的GPU與CPU共享功耗/散熱預算，這可能引入性能分析工具應該揭示的爭用問題（例如，當CPU滿負荷運行時GPU是否被限制）。

    APU的工具在很大程度上與上面討論的CPU和GPU工具重疊，但更強調集成分析。例如，AMD的工具鏈是APU感知的：AMD uProf是一個覆蓋CPU性能（PMU事件、緩存未命中等）的性能分析套件，也可以在支持的APU上與GPU活動關聯。AMD uProf和CodeXL歷史上允許在APU的集成GPU上分析OpenCL內核，報告每個內核的性能計數器。前面提到的新的ROCm Omnitrace明確支持在一個時間線中同時分析CPU和GPU，這對於CPU線程頻繁啟動GPU工作的APU來說是理想的。Omnitrace能夠在CPU端使用二進制插樁和調用棧採樣，同時追蹤GPU內核，有助於在APU上"全息"映射性能。這意味著如果APU上的CPU函數調用GPU內核，該工具可以顯示CPU函數中的時間和GPU內核中的嵌套時間作為同一調用樹的一部分——這對於優化異構代碼至關重要。

    對於消費級APU（如帶有Radeon圖形的AMD Ryzen處理器），開發者通常使用圖形性能分析器（用於遊戲用例）或OpenCL/Vulkan性能分析器進行計算。例如，AMD的Radeon GPU Profiler在集成GPU上的工作方式與獨立GPU相同。統一內存也允許使用標準操作系統性能計數器：在Linux上，AMD的GPU驅動程序通過drm/sysfs暴露某些GPU利用率指標，因此甚至可以使用系統監視器或自定義腳本來記錄GPU活動和CPU活動。使用APU的Windows開發者可能使用Microsoft的PIX或AMD的Radeon Developer工具來分析在集成GPU上運行的DirectX12遊戲——這些工具顯示CPU和GPU時間線，並可以突出顯示CPU是否餓死了GPU或相反。本質上，APU性能分析不需要全新的工具類別，但它受益於能夠緊密關聯CPU和GPU性能的工具。這類似於在獨立GPU系統上進行性能分析，只是CPU-GPU之間的延遲更低，內存是共享的，工具需要考慮這一點（例如，可能出現CPU和GPU在內存上爭用的緩存一致性效應）。

    值得注意的是，集成架構在2010年代中期促進了HSA（異構系統架構）的發展，AMD的工具有HSA特定的性能分析模式。例如，CodeXL包含一個用於AMD APU的HSA性能分析器，可以追蹤HSA內核調度和HSAIL指令。現在這些功能大部分已被吸收到ROCm工具中。本質仍然是：APU需要對整個系統進行性能分析，而不僅僅是孤立地分析"CPU vs GPU"。像Omnitrace、VTune或HPCToolkit（具有異構調用路徑分析）這樣的工具對基於APU的工作負載特別適用，因為它們自然地混合CPU和GPU指標。

    開源與商業解決方案的比較

    在加速器性能分析領域，開源（OSS）和商業/專有解決方案各有優缺點。以下是幾個關鍵方面的比較：

    • 功能深度和硬件訪問： 供應商提供的工具（通常閉源，但往往免費）往往對硬件性能計數器和功能有最全面的訪問權限。例如，NVIDIA的Nsight可以報告SM warp停滯原因和紋理緩存命中率——這些指標由NVIDIA的專有接口暴露，開源工具通常無法獲取。同樣，AMD的專有驅動程序可能向RGP暴露通用工具無法獲得的GPU波前佔用率詳情。OSS工具依賴於發佈或逆向工程的接口；例如，AMD的GPUPerfAPI（開放庫）提供跨平臺計數器訪問，這就是為什麼AMD自己的工具可以開源。開源項目有時缺乏對最新硬件的支持，直到供應商發佈文檔，而商業工具在新GPU發佈第一天就準備就緒（因為供應商負責構建它們）。另一方面，像HPCToolkit這樣的開源工具在某些功能上有創新，如完全自動化的調用棧展開和統計GPU指令採樣，這些在供應商GUI中不可用，表明OSS在某些功能（特別是集成和低開銷方面）可以領先。

    • 可擴展性和定製化： 開源性能分析器（HPCToolkit、TAU等）允許用戶修改或編寫腳本，實現自定義分析或集成到自動化管道中。例如，你可以使用Score-P對代碼進行插樁並以開放追蹤格式（OTF2）輸出追蹤，然後使用自定義分析工具進行後處理——這一切都是因為格式和代碼是開放的。相比之下，商業工具通常將數據鎖定在專有格式中（例如，Nsight的.nsys-rep追蹤文件）需要供應商的查看器，儘管存在一些導出選項（如CSV導出）。OSS方法還促進了社區貢獻——例如，對新編程模型（OpenMP卸載、Kokkos等）的支持通常首先通過社區補丁出現在TAU或Score-P等工具中。

    • 跨供應商支持： 如前所述，開源工具通常更供應商中立。像Vampir或HPCToolkit這樣的單一工具可以在一次運行中處理多種加速器類型，而供應商工具是孤立的（Nsight不會分析AMD GPU，AMD的rocprof不會在NVIDIA上工作）。對於異構環境（例如，在一個系統中有Intel CPU、NVIDIA GPU和可能的Xilinx FPGA），你唯一的希望可能是一個通過插件或標準API（OpenCL、oneAPI等）支持所有這些的開源工具來獲得統一的追蹤。這在研究或多供應商環境中是OSS解決方案的一個優勢。缺點是供應商工具通常針對自己的硬件更加優化——它們可能提供更精緻的UI，或在該平臺上更穩定的數據收集。例如，使用非官方GPU計數器的開源工具如果驅動程序發生變化，可能會變得脆弱或不太準確。

    • 成本和支持： 大多數GPU/DPU的供應商工具是免費的（以啤酒的意義），但閉源。HPC中有一些真正的商業（需要購買）性能工具，如Arm Forge套件（包括MAP性能分析器）——這些帶有專業支持。開源工具是免費的（以言論/啤酒的意義），但支持來自社區或自我專業知識。具有關鍵任務需求的公司有時更喜歡由供應商支持的工具（以幫助解釋結果或獲取bug修復）。話雖如此，大型供應商（NVIDIA、Intel）確實為他們的免費工具提供支持論壇。在網絡等特定領域，一些商業分析器（例如，深度數據包檢測性能分析器）可能來自專業公司並需要許可證——但這些相對罕見。

    在實踐中，環境通常使用組合方式：例如，HPC中心可能使用供應商性能分析器來優化特定GPU上的代碼，但然後集成HPCToolkit或IPM（一個MPI性能分析器）進行迴歸測試和跨系統比較。值得注意的是，開源和閉源工具可以相互補充。開發者可能運行OSS追蹤工具獲取高級概覽，並使用供應商的詳細性能分析器交叉檢查特定內核。GPU領域的一個例子：用戶可以運行使用Score-P插樁的程序獲取整體MPI+GPU時間線，然後使用Nsight Compute放大特定感興趣的GPU內核，檢查其內存吞吐量。這種分層方法發揮了每種工具的優勢。

    特定工作負載的工具映射

    不同的工作負載以不同方式壓力測試加速器，相應地，在每個領域都有特定工具被青睞：

    • 通用計算/HPC： 這些工作負載（科學模擬、線性代數、數據分析）使用GPU獲取吞吐量。性能分析關注內核效率和GPU利用率。像Nsight Compute（用於計算內核分析）或HPCToolkit/Omniperf這樣的工具非常適合。HPC代碼也在數千個GPU上並行運行；詳細跟蹤每一個是不切實際的，因此像HPCToolkit這樣僅增加~1-5%開銷的工具對於大規模運行的性能分析非常寶貴。HPC工作負載通常使用MPI + GPU，因此可以關聯通信和計算的工具（例如，通過Extrae的時間線追蹤，或通過mpiP與GPU性能分析相結合的MPI分析）非常適合。在HPC中的DPU（例如，使用智能網卡進行RDMA），"工作負載"通常只是網絡——這裡關注的是吞吐量和重疊（性能分析確保DPU處理數據傳輸而GPU計算，例如）。工具：網絡基準測試（如用於InfiniBand的IB Profiler）加上GPU性能分析器，查看通信是否與計算重疊。

    • 機器學習/AI： ML訓練結合了繁重的GPU計算和數據管道開銷。分析ML工作負載可能涉及框架級性能分析器：例如，PyTorch Profiler（建立在Kineto上）內部使用CUPTI記錄每個操作的GPU時間，或TensorFlow Profiler同樣捕獲操作和流的時間線。這些產生高級視圖（哪個模型層花費時間）以及低級內核詳情。NVIDIA有一個DLProf工具，與TensorBoard集成，在神經網絡操作的上下文中顯示GPU內核指標。對於多GPU訓練，Nsight Systems可以跟蹤跨GPU的活動（特別是如果使用NCCL進行通信——Nsight可以顯示NCCL調用時間線）。一個新興的挑戰是分佈式訓練的性能分析：像PyTorch Profiler現在有分佈式追蹤，但無縫分析100多個GPU訓練一個模型仍然是一個活躍的開發領域。在DPU方面，AI可能使用DPU進行預處理或移動數據——分析DPU的效果（例如使用它進行數據過濾）涉及監控DPU加速數據攝取的程度（通過吞吐量跟蹤）並確保GPU不會飢餓。未來，DPU上的AI加速器（一些DPU可能包括微型ML核心）可能需要新的性能分析器，但目前大多數AI工作側重於GPU。

    • 網絡和I/O工作負載： 對於DPU或GPU上的純網絡任務（是的，GPU在某些情況下也可以使用CUDA或OpenCL進行數據包處理），性能分析關注延遲和吞吐量。這裡的工具包括數據包生成器（測量管道可以處理多少Mpps）和代碼路徑的追蹤工具。例如，如果使用GPU加速數據包加密，可能使用Nsight確保內核啟動與數據傳輸重疊。如果使用DPU在軟件中運行IDS（入侵檢測），可能使用perf分析它是否受CPU限制，並使用NIC計數器查看丟包。網絡工作負載通常需要實時追蹤（捕獲抖動峰值），因此可能使用基於eBPF的監視器甚至硬件遙測（如P4運行時日誌）。也有人對使用GPU進行網絡（通過CUDA管道的GPU加速NIC卸載）感興趣，這將涉及GPU和網絡性能分析——但這相當小眾和實驗性。

    • 圖形和可視化： 對於GPU（特別是遊戲機或筆記本電腦中的APU）上的遊戲引擎或VR應用，RenderDoc、Nsight Graphics和平臺性能分析器（例如用於Metal的Apple的Xcode Instruments）專為測量幀時間、GPU管線階段和CPU-GPU同步而設計。圖形工作負載通常受GPU著色器吞吐量或CPU繪製調用提交率的限制。性能分析映射到檢查GPU的幀時間預算是否被超出以及原因（哪個階段——頂點著色？片段？內存？）。這些工具通常提供專門的可視化（HUD疊加層、幀刮刀）是一般計算性能分析器不提供的。對於處理圖形的APU，還必須考慮CPU和GPU共享內存帶寬——圖形調試器可以顯示CPU內存流量（例如，更新紋理）是否影響GPU。此外，在專業可視化（CAD等）中，GPU內存使用可能是限制因素；像NVIDIA的Nsight或AMD的RGPA這樣的工具可以分析VRAM使用情況和緩存行為，以優化大型模型。

    本質上，每種處理單元類型在特定領域都有使用，性能分析解決方案相應地發展——但也存在趨同。現代AI應用可能涉及GPU用於計算，CPU用於編排，DPU用於數據加載，所有這些都在一個管道中。這提出了對多加速器性能分析的需求——跟蹤一個操作在CPU、DPU和GPU之間移動的能力。今天這通常意味著運行多個工具並手動關聯時間戳。例如，可能使用Nsight跟蹤GPU，同時在網絡端運行tcpdump或NIC計數器，然後對齊日誌。這種多組件工作流程很麻煩，表明有機會對異構工作流程進行更集成的性能分析。

    現有工具鏈的侷限和挑戰

    儘管有眾多已討論的工具，但在對GPU、DPU和APU進行性能分析時，從業者面臨幾個持續存在的挑戰：

    • 碎片化和供應商鎖定： 如前所述，每個供應商的加速器通常帶有一個孤立的工具鏈。這意味著在一種工具中的專業知識不容易轉移到另一種，混合硬件會導致多個工具。它還有鎖定風險：使用專有工具進行的優化可能依賴於供應商特定的功能。沒有像"perf"這樣的通用標準可以普遍覆蓋所有加速器類型（儘管在CPU上，perf本身僅限於Linux）。GPU供應商之間缺乏通用性能計數器接口就是一個典型例子——開發者必須使用CUDA特定或ROCm特定的API，這使得可移植的性能分析變得困難。對於DPU，它們相對較新，甚至沒有廣泛採用的第三方性能分析器——你使用DPU供應商提供的任何工具。這種碎片化不僅使開發者的生活複雜化，也使試圖公平比較平臺的研究者複雜化。

    • 有限的可見性（"黑盒"問題）： 加速器性能的某些方面對當前的性能分析器來說實際上是黑盒。例如，GPU內部調度（warp如何調度，L2緩存行如何驅逐）可能不會通過計數器完全暴露。同樣，如果DPU的數據包加速器是FPGA或ASIC，外部工具可能只看到吞吐量數字，而不是為什麼它在X Gbps飽和（例如，NIC內部的微架構細節）。即使使用NVIDIA的計數器，也經常有未記錄的指標或難以解釋的指標。這種有限的可見性通常是設計上的（IP保護），但阻礙了優化。另一個可見性問題出現在閉源工作負載中：如果你在GPU上分析第三方庫，你可能會看到內核名稱和時間，但不知道它內部做了什麼。像HPCToolkit這樣的工具通過將成本歸因於指令（即使沒有源代碼）來提供幫助，但通常很難優化你無法檢查的內容。

    • 開銷與侵入性： 許多精確的追蹤工具擾動它們所測量的性能。基於插樁的追蹤（在每個內核啟動或每個數據包上插入鉤子）可能導致海森堡效應，即測量行為改變時序。雖然基於採樣的方法緩解了這一點，但它們用較低的開銷換取細節。總是存在一個挑戰，即找到正確的平衡：收集多少數據和以什麼頻率，以獲得代表性概況而不會淹沒在開銷或數據量中。高開銷工具必須限於測試環境，意味著你可能無法捕獲只在規模或生產環境中顯現的問題。相反，超輕量級監視器可能只標記"GPU利用率低"，但不解釋原因。彌合這一差距仍然是一個持續的挑戰。

    • 併發和排序問題： 分析多線程、多流工作負載可能遇到對齊事件的問題。例如，來自不同GPU或不同設備的時間線追蹤可能有時鐘偏差，使得確定事件的真實順序變得棘手。即使在一個GPU上，硬件也可以併發執行許多內核（在不同的SM上或使用異步流），可視化或理解重疊活動很複雜。工具嘗試（例如，Nsight Systems在時間線上顯示重疊內核），但隨著系統擴展，人們面臨我們可能稱之為"事件爆炸"問題：需要推理的事件太多。過濾和專注於正確的子集很困難。工具才剛開始引入更智能的過濾（例如，只追蹤長於X微秒的內核，或僅在GPU利用率下降時追蹤GPU活動等）。

    • 缺乏多加速器協調： 今天的工具在很大程度上是按設備孤立運行的。如果你有一個帶有CPU、GPU、DPU、FPGA的異構節點，每個可能單獨分析，產生用戶必須關聯的單獨報告。假設一個性能問題是由於GPU吞吐量和NIC吞吐量不匹配導致的——GPU性能分析器可能只顯示GPU空閒20%的時間（等待數據），而NIC監視器顯示隊列100%利用率——由工程師來關聯這些並推斷原因（網絡綁定）。理想情況下，性能分析器會自動捕獲此類跨設備依賴性（例如，視覺提示表明GPU空閒與NIC飽和相關）。實現這一點需要全面視圖，也許是可以跨設備鏈接的標準化追蹤事件（例如，NIC上的"幀傳遞"事件可以與"GPU上處理的幀"事件關聯）。沒有通用標準，這種關聯主要是手動的或通過臨時插樁（在應用代碼中插入時間戳）。

    • 縮放和大數據問題： 在分析大規模工作負載時（想想1000個GPU或處理每秒數百萬數據包的DPU），性能分析數據量可能非常龐大。存儲和分析即使是幾秒鐘操作的追蹤日誌可能都是非常重要的。數據減少是一個挑戰——如何有意義地總結性能數據。當前工具提供一些總結（如平均內核時間、前10大內存消費者等），但需要更多自動化總結，可能採用分層或統計技術來壓縮追蹤。HPC中心通過選擇性追蹤（僅在少數等級上捕獲等）或使用採樣來處理這個問題。未來的工具可能包含在線分析，工具本身在收集數據時進行一些處理（例如，計算分佈而不是記錄每個事件）。

    • 教育和可用性： 最後，值得注意的是一個實際挑戰：學習曲線。每個工具通常都有自己的GUI或輸出格式，理解"warp序列化"或"bank衝突"或"DPU緩存命中"等指標需要一些架構知識。這些加速器上的性能分析在某種程度上是一門黑魔法，雖然工具提供數據，但理解它並不總是直接的。屋頂線模型等努力試圖簡化解釋，但用戶仍然很難從性能分析器輸出轉變為具體優化。這部分是教育挑戰——文檔和培訓需要伴隨工具。這也是工具構建者的設計挑戰，以直觀的方式呈現數據（例如，Nvidia現在通常直接集成AI性能指標，如"Tensor Cores的利用率"，告訴ML工程師他們如何利用GPU）。

    總之，雖然當前用於GPU、DPU和APU的追蹤和性能分析工具強大且必不可少，但它們在一個高度專業化和碎片化的環境中運作，存在可見性差距和集成缺陷。克服這些侷限需要協作努力——硬件供應商（開放接口）、工具開發者（創建更智能、標準的工具）和研究社區（開創低開銷和組合追蹤的新技術）之間的協作。

    當前研究方向和新興趨勢

    加速器追蹤/性能分析領域正在積極發展。以下是幾個關鍵的研究和開發方向：

    • 低開銷、常時開啟的性能分析： 如前所述，借鑑操作系統遙測（eBPF、硬件性能監視器）的技術正在適應加速器。Meta的連續GPU性能分析器和GPUprobe等工具表明，可以在生產環境中以最小的開銷收集有用的數據。我們預計這一領域會有更多工作：例如，連續DPU監控集成到數據中心可觀察性棧中（類似於GPU的DCGM）——可能使用eBPF監控DPU NIC驅動程序或使用硬件內置遙測（許多NIC有用於數據包調度、隊列佔用等的遙測流，可以利用這些）。對於GPU，研究人員正在探索基於採樣的性能分析以進一步減少開銷。NVIDIA的最新架構支持PC採樣，GPU定期採樣其程序計數器並報告正在執行哪些指令以及它們是否停滯。這可以在後臺進行，幾乎不會干擾。HPCToolkit已經在NVIDIA GPU上利用這一點來採樣指令並推導停滯分析。未來的工具可能擴展此類採樣，以獲取GPU活動的統計跟蹤，而無需對每個內核啟動進行插樁。

    • 統一和標準化接口： 一個反覆出現的主題是跨供應商缺乏標準化。有人呼籲建立供應商中立的GPU性能分析API——例如，OpenGL社區過去曾建議一個跨供應商統一的GPU性能計數器API。在計算領域，類似於CPU的PAPI（性能API）的GPU版本將是有價值的。我們看到早期步驟：Khronos Group的OpenCL和Vulkan API有性能查詢擴展（如Vulkan的VK_KHR_performance_query）允許應用程序以標準化方式收集一些計數器。此外，Intel的oneAPI旨在為加速器提供統一接口（Level Zero），包括工具支持。雖然oneAPI以Intel為中心，但它為抽象性能分析設立了先例：理論上，應用程序可以使用oneAPI在CPU、GPU和FPGA上使用單一工具進行性能分析——但前提是其他供應商採用或適應它。另一個推動力是硬件的OpenTelemetry——目前OpenTelemetry（在雲中流行用於追蹤請求）不涵蓋內部硬件事件，但可以設想將其擴展到CPU、加速器和網絡事件，用於異構工作負載的分佈式追蹤。

    • AI在性能分析中的集成： 隨著性能數據的複雜性（特別是來自細粒度追蹤），有興趣使用機器學習輔助性能分析。研究項目已經研究了從部分追蹤預測性能或從計數器特徵自動分類瓶頸的學習模型。例如，ML模型可能學習計數器模式，表明內存帶寬瓶頸與計算綁定，自動化人類專家手動使用屋頂線模型做的事情。雖然在工具中尚未主流化，但一些性能分析器（如Intel Advisor的自動屋頂線分析，或NVIDIA在Nsight Compute中的引導分析）納入了啟發式指導，可能發展為ML驅動的建議。目標是幫助開發者更容易解釋性能分析數據的洪流。

    • 因果追蹤和因果性能分析： 傳統性能分析被動觀察性能。一個較新的研究方向是因果性能分析，性能分析器通過擾動執行來實驗，以測量對性能的影響（例如，人為減慢一個組件，看看其他組件是否空閒，確定瓶頸的因果關係）。Omnitrace提到對因果性能分析的支持暗示這類技術正在為GPU/CPU組合實施。因果追蹤可以識別，例如，GPU內核X完成延遲是導致CPU任務Y延遲的原因，通過觀察如果X更快或更慢，時間如何變化。這是一種高級功能，有潛力解開異步管道中的複雜依賴關係。

    • 多加速器和分佈式協調： 隨著系統集成CPU + 各種加速器（GPU、DPU、FPGA、TPU等），一個研究挑戰是在它們之間協調性能分析。當工作的部分發生在不同的芯片上，每個都有自己的時鐘和追蹤緩衝區時，我們如何獲得一個連貫的時間線或概況？HPC中的Extrae/Paraver等工具可以通過對齊時間戳（假設時鐘同步）合併來自CPU和GPU的追蹤，並允許一起分析它們。我們期待在這方面的進一步發展，可能使用標準時間戳（可以使用PTP——精密時間協議——同步主機和DPU之間的時間，例如）。此外，正在探索跨工具協調觸發器——例如，當網絡事件發生時啟動GPU性能分析器。一些當前工具允許觸發器（Nsight可以基於CUDA API調用或標記啟動/停止）；將其擴展到跨設備（當DPU的數據包隊列溢出時啟動GPU追蹤）對於診斷跨棧性能問題（如緩慢的GPU導致智能網卡上的數據包積壓）可能非常有用。

    • 新型加速器的更好性能分析： 雖然本報告主要關注GPU、DPU和APU，但加速器世界還包括FPGA、AI ASIC（例如Google的TPU）等。每一種都在孵化自己的工具——Xilinx（AMD）FPGA有用於硬件內核的Vivado和Vitis分析器，Google TPU在TensorBoard中有性能分析器等。一個明確的方向是將這些整合在一起。如果一個雲有CPU、GPU、DPU、TPU一起工作，理想情況是有一個單一窗口來觀察它們。行業聯盟最終可能在加速器遙測方面合作制定開放標準（類似於OpenCL是計算的標準）。在此之前，研究通常會介入：例如，關於通過結構內監視器監控數據中心FPGA的學術工作，或在其他設備上使用類似eBPF的技術。

    總之，性能分析/追蹤研究正朝著使這些工具更普遍、智能和統一的方向發展。目標是減輕開發者手動插樁和關聯來自不同來源的性能數據的負擔，而是提供更智能的工具，適用於當今數據中心複雜的異構系統。

    結論

    加速器的追蹤和性能分析已經變得與早期對CPU進行性能分析一樣關鍵。我們現在擁有針對不同硬件和用例的廣泛工具：從NVIDIA的Nsight套件和AMD的ROCm工具進行深度GPU分析，到像HPCToolkit這樣用於整體性能分析的開源框架，再到基於eBPF的新興方法，實現連續監控。GPU享有最成熟的工具支持（反映了它們在計算中的較長曆史），而DPU和其他領域特定加速器正在趕上，擁有自己的新興性能分析器和遙測系統。APU說明了需要能夠無縫地跨越傳統處理器邊界進行性能分析的工具，因為計算正朝著緊密集成的異構設計發展。

    本綜述強調了開源和商業解決方案都扮演著重要角色：開源工具促進跨平臺敏捷性和創新，而供應商工具利用專有知識為其硬件提供最大洞察。最佳結果通常來自於將它們結合使用。在ML、網絡和圖形等專業領域，領域特定的性能分析能力增強了通用工具，提供所需的視角（例如，從神經網絡層的角度查看GPU時間線，或在CPU週期上下文中的網絡吞吐量）。

    展望未來，趨勢指向更多集成（跨加速器的統一時間線）、自動化（智能分析）和低開銷可觀察性成為標準。研究正在積極解決許多當前差距，從標準化性能指標到使用因果性能分析和ML驅動分析等新技術來解釋性能數據。同時，供應商鎖定和黑盒硬件等挑戰將需要行業合作，也許需要推動更開放的硬件遙測接口。

    總結起來，旨在優化加速器驅動系統的開發者和工程師應採取混合方法：利用供應商特定性能分析器的豐富功能進行詳細分析，使用開源和跨平臺工具獲取跨多樣化硬件的"大圖景"，並關注可以採用的新興工具，以改進連續性能監控。通過結合這些工具和技術，可以獲得對任何工作負載上GPU、DPU和APU性能的全面理解——從單個GPU內核的指令停滯到整個異構管道的端到端行為。這種深入而廣泛的性能分析能力對於充分利用現代加速器在通用和領域特定應用中的計算能力至關重要。

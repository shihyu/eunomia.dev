    eBPF 進階: 內核新特性進展一覽

    Linux 內核在 2022 年主要發佈了 5.16-5.19 以及 6.0 和 6.1 這幾個版本，每個版本都為 eBPF 引入了大量的新特性。本文將對這些新特性進行一點簡要的介紹，更詳細的資料請參考對應的鏈接信息。總體而言，eBPF 在內核中依然是最活躍的模塊之一，它的功能特性也還在高速發展中。某種意義上說，eBPF 正朝著一個完備的內核態可編程接口快速進化。

    BPF kfuncs

    BPF子系統暴露了內核內部算法和數據結構的許多方面；這自然導致了對在內核變化時保持接口穩定性的關注。長期以來，BPF對用戶空間不提供接口穩定性保證的立場似乎一直有點問題；過去，內核開發者發現他們不得不維護那些不打算穩定的接口。現在BPF社區開始考慮至少為它的一些接口提供明確的穩定性承諾可能意味著什麼。

    BPF允許由用戶空間加載的程序被附加到大量鉤子中的任何一個，並在內核中運行--在子系統的驗證器得出這些程序不會損害系統的結論之後。一個程序將獲得由它所連接的鉤子提供給它的內核數據結構的訪問權。在某些情況下，程序可以直接修改這些數據，從而直接影響內核的運行；在其他情況下，內核將對BPF程序返回的值採取行動，例如，允許或不允許某項操作。

    還有兩種機制，內核可以通過它們使BPF程序獲得額外的功能。幫助函數（或 "helpers"）是為提供給BPF程序而編寫的特殊函數；它們從擴展BPF時代開始就存在了。被稱為kfuncs的機制比較新；它允許任何內核函數被提供給BPF，可能會有一些限制。Kfuncs更簡單、更靈活；如果它們首先被實現，那麼似乎不太可能有人會在後來添加幫助器。也就是說，kfuncs有一個重要的限制，即它們只能被JIT編譯的BPF代碼訪問，所以它們在缺乏JIT支持的架構上是不可用的（這個列表目前包括32位Arm和RISC-V，儘管增加這兩種支持的補丁正在開發中）. 每個kfunc都為BPF程序提供了一些有用的功能，但幾乎每個kfunc都暴露了內核內部工作方式的某些方面。

    • Reconsidering BPF ABI stability: https://mp.weixin.qq.com/s/wYDSXuwVgmGw-wmFgBNJcA
    • Documentation/bpf: Add a description of "stable kfuncs" https://www.spinics.net/lists/kernel/msg4676660.html

    Bloom Filter Map：5.16

    布隆過濾器是一種節省空間的概率數據結構，用於快速測試一個元素是否存在於一個集合中。在布隆過濾器中，假陽性是可能的，而假陰性則不可能。

    這個補丁集包括布隆過濾器中可配置數量的哈希值和條目的基準測試。這些基準大致表明，平均而言，使用3個哈希函數是最理想的選擇之一。當比較hashmap查找中使用3個哈希值的bloom filter和不使用bloom filter的hashmap查找時，使用bloom filter的查找對於5萬個條目大約快15%，對於10萬個條目快25%，對於5萬個條目快180%，對於1百萬個條目快200%。

    • BPF: Implement bloom filter map https://lwn.net/Articles/868024/

    Compile Once – Run Everywhere：Linux 5.17

    Linux 5.17 為 eBPF 添加了一次編譯到處執行（Compile Once – Run Everywhere，簡稱 CO-RE），大大簡化了 eBPF 程序處理多版本內核兼容時的複雜性以及循環邏輯的處理。

    eBPF 的一次編譯到處執行（簡稱 CO-RE）項目藉助了 BPF 類型格式（BPF Type Format, 簡稱 BTF）提供的調試信息，再通過下面的四個步驟，使得 eBPF 程序可以適配不同版本的內核：

    • 第一，在 bpftool 工具中提供了從 BTF 生成頭文件的工具，從而擺脫了對內核頭文件的依賴。
    • 第二，通過對 BPF 代碼中的訪問偏移量進行重寫，解決了不同內核版本中數據結構偏移量不同的問題。
    • 第三，在 libbpf 中預定義不同內核版本中數據結構的修改，解決了不同內核中數據結構不兼容的問題。
    • 第四，在 libbpf 中提供一系列的內核特性探測庫函數，解決了 eBPF 程序在不同內核內版本中需要執行不同行為的問題。比如，你可以用 bpf_core_type_exists() 和bpf_core_field_exists() 分別檢查內核數據類型和成員變量是否存在，也可以用類似 extern int LINUX_KERNEL_VERSION __kconfig 的方式查詢內核的配置選項。

    採用這些方法之後，CO-RE 就使得 eBPF 程序可以在開發環境編譯完成之後，分發到不同版本內核的機器中運行，並且也不再需要目標機器安裝各種開發工具和內核頭文件。所以，Linux 內核社區更推薦所有開發者使用 CO-RE 和 libbpf 來構建 eBPF 程序。實際上，如果你看過 BCC 的源代碼，你會發現 BCC 已經把很多工具都遷移到了 CO-RE。

    • eBPF多內核版本兼容詳解： https://time.geekbang.org/column/article/534577
    • BPF CO-RE reference guide：https://nakryiko.com/posts/bpf-core-reference-guide/

    bpf_loop() 輔助函數：5.17

    擴展的BPF虛擬機的主要特徵之一是內置於內核的驗證器，它確保所有BPF程序都能安全運行。不過，BPF開發者常常認為驗證器有點喜憂參半；雖然它能在很多問題發生之前抓住它們，但它也很難讓人滿意。將其與一個善意但受規則約束且挑剔的官僚機構相提並論並不是完全錯的。Joanne Koong提出的 bpf_loop() 建議是為了讓一種類型的循環結構更容易取悅BPF的官僚們。

    簡而言之，這就是Koong的補丁的目的。它增加了一個新的輔助函數，可以從BPF代碼中調用。

        long bpf_loop(u32 iterations, long (*loop_fn)(u32 index, void *ctx),
          void *ctx, u64 flags);

    對 bpf_loop() 的調用將導致對 loop_fn() 的迭代調用，迭代數和傳入的 ctx 作為參數。flags 值目前未使用，必須為零。loop_fn() 通常將返回0；返回值為1將立即結束迭代。不允許有其他的返回值。

    不像 bpf_for_each_map_elem() 受限於 bpf map 大小，bpf_loop() 的循環次數高達 1<<23 = 8388608（超過 8 百萬）次；大大地擴展了 bpf_loop() 的應用場景。不過，bpf_loop() 並沒有受限於 BPF 指令數（1 百萬條），這是因為循環發生在 bpf_loop() 幫助函數內部。

    • A different approach to BPF loops：https://lwn.net/Articles/877062/
    • eBPF Talk: 實戰經驗之 loop：https://mp.weixin.qq.com/s/neOVsMNVWFbwpTSek-_YsA

    BPF_LINK_TYPE_KPROBE_MULTI：5.18

    這個補丁集增加了新的鏈接類型BPF_TRACE_KPROBE_MULTI，它通過Masami製作的fprobe API [1]來連接kprobe程序。fprobe API允許一次在多個函數上附加探針，速度非常快，因為它工作在ftrace之上。另一方面，它將探測點限制在函數入口或返回。

    • bpf: Add kprobe multi link：https://lwn.net/Articles/885811/

    動態指針和類型指針：5.19

    BPF程序中的所有內存訪問都使用驗證器進行安全性靜態檢查，驗證器在允許程序運行之前對其進行全面分析。雖然這允許 BPF 程序在內核空間中安全運行，但它限制了該程序如何使用指針。直到最近，一個這樣的限制是在 BPF 程序中被指針引用的內存區域的大小必須在加載 BPF 程序時靜態知道。Joanne Koong 最近設置的一個補丁集增強了 BPF，以支持使用指向動態大小的內存區域的指針加載程序。

    Koong 的補丁集增加了對訪問 BPF 程序中動態大小的內存區域的支持，其中包含一個名為 dynptrs 的新特性。dynptrs 背後的主要思想是將指向動態大小的數據區域的指針與驗證器和一些 BPF 輔助函數使用的元數據相關聯，以確保對該區域的訪問是有效的。Koong 的補丁集在一個新定義的類型中創建了這種關聯，稱為struct bpf_dynptr。這種結構對 BPF 程序是不透明的。

    USDT：5.19

    靜態跟蹤點（tracepoint），在用戶空間也被稱為 USDT（用戶靜態定義的跟蹤）探針（應用程序中感興趣的特定位置），跟蹤器可以在此處掛載檢查代碼執行和數據。它們由開發人員在源代碼中明確定義，通常在編譯時用 “–enable-trace” 等標誌啟用。靜態跟蹤點的優勢在於它們不會經常變化：開發人員通常會保持穩定的靜態跟蹤 ABI，所以跟蹤工具在不同的應用程序版本之間工作，這很有用，例如當升級 PostgreSQL 安裝並遇到性能降低時。

    • eBPF 概述：第 5 部分：跟蹤用戶進程：https://www.ebpf.top/post/ebpf-overview-part-5/
    • Using user-space tracepoints with BPF：https://lwn.net/Articles/753601/

    bpf panic：6.1

    BPF子系統的關鍵賣點之一是加載BPF程序是安全的：BPF驗證器在允許加載之前確保該程序不會傷害內核。隨著更多的功能被提供給BPF程序，這種保證也許會失去一些力量，但即便如此，看到 Artem Savkov 的這個提議加入了一個明確設計為使系統崩潰的BPF助手，可能會讓人有點吃驚。如果這個補丁集以類似於目前的形式被合併，它將是一個新時代的預兆，即至少在某些情況下，BPF程序被允許公開地進行破壞。

    正如 Savkov 所指出的，BPF 的主要用例之一是內核調試，這項任務也經常因為存在一個適時的崩潰轉儲而得到幫助。通過使內核的panic() 函數對BPF程序可用，Savkov試圖將這兩者結合起來，允許BPF程序在檢測到表明開發人員正在尋找的問題的條件時導致崩潰，並創建崩潰轉儲。Savkov似乎不是唯一想要這種能力的人；Jiri Olsa指出，他也收到了關於這種功能的請求。

    • The BPF panic function: https://lwn.net/Articles/901284/

    BPF 內存分配器、鏈表：6.1

    本系列介紹了用戶定義的BPF對象在程序中的 BTF 類型。這允許BPF程序分配他們自己的對象，建立他們的自己的對象層次，並使用由BPF 運行時提供的基本構件來靈活地建立自己的數據結構。

    然後，我們介紹了對單一所有權BPF鏈表的支持。它可以放在BPF映射或分配的對象中，並把這些被分配的對象作為元素。它作為一個侵入性的集合工作。這樣做的目的是為了在將來使分配的對象成為多個數據結構的一部分。

    這個補丁和未來補丁的最終目標是允許人們在 BPF C 中做一些有限的內核式編程，並允許程序員靈活地從基本的構建塊中靈活地構建自己的複雜數據結構。

    關鍵的區別在於，這種程序是經過驗證的，是安全的，保存系統的運行時完整性，並被證明是沒有錯誤的

    具體的功能包含

    • 分配對象
    • bpf_obj_new, bpf_obj_drop 來分配和釋放對象
    • 單一所有權的BPF鏈表
    • 在 BPF maps 中支持它們
    • 在分配的對象中支持它們
    • 全局自旋鎖。
    • 在被分配對象中的自旋鎖。

    user ring buffer 6.1

    這個補丁集定義了一個新的映射類型，BPF_MAP_TYPE_USER_RINGBUF，它在一個環形緩衝器上提供了單用戶空間生產者/單內核消費者的語義。 除了新的映射類型外，還增加了一個名為bpf_user_ringbuf_drain()的輔助函數，它允許BPF程序指定一個具有如下簽名的回調，樣本由輔助函數發佈到該回調。

    void（struct bpf_dynptr *dynptr, void *context）。

    然後程序可以使用bpf_dynptr_read()或bpf_dynptr_data()輔助函數來安全地從dynptr中讀取樣本。目前沒有可用的輔助函數來確定樣本的大小，但是如果需要的話，可以很容易地添加一個。
